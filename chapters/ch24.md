# 24장 GitHub에 올리기

!!! note "이 장에서 배우는 것"
    - `my-map` 프로젝트를 Git 저장소로 만들고 첫 커밋을 남깁니다
    - `.gitignore`를 최종 점검합니다 — `.env`와 `node_modules`를 왜 빼는지 확실히 이해합니다
    - `gh repo create my-map --public --source=. --push` 한 줄로 프로젝트를 깃허브에 올립니다
    - GitHub 웹 화면에서 올라간 파일을 눈으로 검수하고, `.env`가 없는지 반드시 확인합니다
    - 앞으로 평생 쓸 커밋 메시지 습관을 만듭니다

---

이제 이 책의 마지막인 5부에 들어왔습니다. 지금까지 8장에서 빈 폴더로 출발해 9장에서 지도를 띄우고, 11장에서 마커를 찍고, 13~15장에서 말풍선과 필터와 검색을 붙이고, 16~19장에서 장소를 추가하고 저장하고 관리하고, 20~22장에서 내 위치와 공유와 클러스터러를 만들고, 23장에서 스마트폰 화면에도 맞췄습니다. `my-map`에 이제 필요한 기능이 다 들어갔습니다.

그런데 이 앱은 지금 여러분의 컴퓨터 안에만 있습니다. 다른 사람에게 보여 주려면 노트북을 들고 가야 하고, 하드디스크가 고장 나면 함께 사라집니다. 5부에서는 이 앱을 인터넷에 공개합니다. 그 첫 단계로 이번 장에서 프로젝트를 깃허브에 올립니다. 다음 장에서 다룰 배포(GitHub Pages)도, 마지막 장의 README 작성도 코드가 깃허브에 올라가 있어야 진행할 수 있습니다.

이번 장에서 할 일은 5장에서 이미 한 번 연습했습니다. `hello-github` 연습 저장소를 만들면서 `git init` → `commit` → `gh repo create` 순서를 밟아 보았습니다. 이번에는 같은 순서를 실제 프로젝트에 적용합니다. 다만 이 프로젝트에는 카카오 JavaScript 키가 든 `.env` 파일이 있고, 이 파일은 올라가면 안 됩니다. 그래서 이번 장의 절반은 무엇을 빼고 올릴지를 정하는 데 씁니다.

## 24.1 올리기 전 점검: 무엇을 빼고 올릴 것인가

이삿짐을 쌀 때 모든 물건을 다 싸지는 않습니다. 쓰레기는 버리고, 냉장고 속 음식은 비우고, 귀중품은 따로 챙깁니다. 저장소에 올릴 짐을 쌀 때도 똑같습니다. 프로젝트 폴더 안의 모든 파일이 깃허브에 갈 자격이 있는 건 아닙니다. `my-map` 폴더를 열어 짐을 분류해 봅시다.

올릴 것. 앱을 다시 만들 수 있는 파일을 올립니다. `index.html`과 `src` 폴더의 자바스크립트와 CSS 전부, 그리고 `package.json`이 그 대상입니다. 이 파일들만 있으면 어떤 컴퓨터에서든 우리 앱을 다시 실행할 수 있습니다.

뺄 것. 두 가지를 빼는데, 빼는 이유는 서로 정반대입니다.

먼저 인증 키가 들어 있는 `.env`를 뺍니다. 8장에서 카카오 JavaScript 키를 코드에 직접 적지 않고 `.env` 파일에 넣었습니다. 잠시 후 저장소를 `--public`으로, 누구나 볼 수 있게 만듭니다. 그러면 저장소 안의 모든 파일이 검색에도 걸리는 공개 문서가 됩니다. 실제로 공개 저장소에 올라간 API 키를 자동으로 수집하는 프로그램이 계속 동작하고 있습니다. 우리 카카오 키는 7장에서 등록한 도메인에서만 동작하지만, 그렇더라도 키는 공개하지 않습니다.

그리고 `node_modules`는 키가 들어 있어서가 아니라 용량이 크고 다시 만들 수 있기 때문에 뺍니다. 이 폴더에는 npm이 설치한 패키지가 들어 있는데, 파일이 수천에서 수만 개이고 용량도 수십에서 수백 메가바이트에 이릅니다. 그런데 이 폴더는 `package.json`만 있으면 `npm install` 명령 한 번으로 다시 만들어집니다. 그래서 `package.json`을 올리면 `node_modules`는 빼도 됩니다. 대부분의 프로젝트가 이렇게 하므로, `node_modules`가 통째로 올라간 저장소는 설정이 잘못된 것으로 봅니다.

이 "뺄 목록"을 적어 두는 파일이 바로 `.gitignore`였습니다. 8장에서 `.env`를 만들 때 Claude Code가 한 번 점검해 줬지만, 그때는 저장소를 만들기 한참 전이었습니다. 올리기 직전인 지금, 마지막으로 재점검합시다. 바이브코딩답게 점검도 시킵니다.

!!! tip "이렇게 물어보세요"
    > my-map 프로젝트를 깃허브 공개 저장소에 올리기 전 점검을 해줘. .gitignore에 .env와 node_modules, dist가 빠짐없이 들어 있는지 확인하고, 없으면 추가해줘. 그리고 이 프로젝트에서 절대 공개되면 안 되는 파일이 또 있는지 목록으로 보고해줘.

Claude Code가 `.gitignore`를 열어 확인하고, 부족한 항목이 있으면 채워 넣은 뒤 보고합니다. 점검이 끝난 `.gitignore`에는 최소한 이 세 줄이 있어야 합니다.

```
node_modules
dist
.env
```

한 줄씩 읽어 봅시다. `node_modules`는 방금 이야기한 패키지 폴더이고, `.env`에는 키가 들어 있습니다. `dist`는 25장에서 `npm run build`를 실행하면 생기는 빌드 결과물 폴더입니다. 이것도 소스코드만 있으면 다시 만들 수 있으므로 뺍니다. Vite 템플릿의 `.gitignore`에는 이 밖에도 `*.local`, 로그 파일, 에디터 설정 폴더 같은 항목이 들어 있습니다. 모두 다시 만들 수 있거나 내 컴퓨터에서만 의미 있는 파일이라는 같은 기준으로 골랐습니다.

![점검을 마친 .gitignore 파일](images/ch24/ch24-f01.png){ width="620" }

!!! warning "주의"
    `.gitignore`는 앞으로의 커밋에서만 파일을 제외하고, 이미 커밋된 파일을 지워 주지는 않습니다. Git은 변경 이력을 기록하는 도구라서, 한번 커밋에 들어간 `.env`는 나중에 파일을 지우고 다시 커밋해도 이전 커밋에 그대로 남습니다. 깃허브에서 커밋 이력을 열어 보면 누구나 그 내용을 볼 수 있습니다. 그래서 순서가 중요하니, 반드시 `.gitignore` 점검을 먼저 하고 커밋은 그다음에 합니다. 이미 `.env`가 커밋된 뒤라면 이 장 끝의 24.4절을 따라 주세요.

## 24.2 git init에서 첫 커밋까지

올릴 것과 뺄 것을 정했으니 이제 커밋을 시작합니다. 먼저 `my-map` 폴더의 터미널에서 현재 상태를 확인합시다. 3장에서 배운 상태 확인 명령을 씁니다.

```powershell
git status
```

여기서 여러분은 둘 중 하나의 화면을 만납니다.

경우 1. `fatal: not a git repository ...` 라는 오류가 나온다면 놀랄 것 없이 지금부터 함께 만들면 됩니다. `npm create vite`는 폴더와 파일만 만들어 줄 뿐 Git 저장소로 초기화해 주지는 않습니다. 그동안 한 번도 `git init`을 하지 않았다면 이 오류가 나오는 것이 맞습니다.

경우 2. 파일 목록이 나온다면 3장에서 이야기한 대로 중간중간 커밋을 남겨 온 것입니다. 이미 저장소가 있으므로 아래에서 `git init`은 건너뛰고, 남은 변경분을 커밋하는 부분부터 따라오면 됩니다.

이번에도 Claude Code에게 통째로 시켜 보겠습니다. 5장의 연습 프롬프트와 비슷하지만, 이번에는 점검 조건을 함께 겁니다.

!!! tip "이렇게 물어보세요"
    > my-map 프로젝트를 git 저장소로 초기화하고 첫 커밋을 만들어줘. 커밋 전에 git status로 커밋될 파일 목록을 나에게 먼저 보여주고, .env나 node_modules가 목록에 있으면 멈추고 알려줘. 커밋 메시지는 "지도 웹앱 완성: 마커·필터·검색·저장·공유"로 해줘.

프롬프트에 담긴 태도를 눈여겨보세요. 그냥 "커밋해 줘"가 아니라 "커밋될 목록을 먼저 보여 주고, 위험 신호가 있으면 멈춰라"라는 안전 조건을 걸었습니다. 에이전트에게 일을 맡기더라도 확인 절차는 사람이 정합니다. 1장에서 이야기한 작게 시키고 확인하는 방식을 그대로 지킨 것입니다. Claude Code는 승인을 받아 가며 대략 다음 명령들을 실행합니다.

```powershell
git init
git status
git add -A
git commit -m "지도 웹앱 완성: 마커·필터·검색·저장·공유"
```

실행된 명령을 한 줄씩 함께 읽어 봅시다.

- `git init` — 이 폴더에 `.git`이라는 숨김 폴더를 만들어 역사 기록을 시작합니다. 아직 아무것도 기록되지 않은, 빈 장부를 편 상태입니다.
- `git status` — 커밋 후보 파일들을 출력합니다. 여기가 오늘의 검문소입니다.
- `git add -A` — 모든 변경 파일을 **스테이지**(기록 대기석)에 올립니다. 3장의 비유를 다시 쓰면, 사진 찍을 사람들을 촬영장에 세우는 단계입니다.
- `git commit -m "..."` — 대기석에 오른 모습 그대로 역사에 도장을 찍습니다. `-m` 뒤가 이 커밋의 이름표입니다.

검문소에서 무엇을 봐야 할까요? `git status`의 출력에서 Untracked files 목록을 훑어보세요. `index.html`, `package.json`, `package-lock.json`, `.gitignore`, `src/` 같은 이름들이 보이면 정상입니다. 반대로 `.env`나 `node_modules/`가 보이면 절대 진행하면 안 됩니다. 24.1절의 `.gitignore` 점검으로 돌아가야 합니다. `.gitignore`가 제 역할을 하고 있다면 Git이 두 파일을 아예 다루지 않으므로 목록에도 나타나지 않습니다.

![커밋 전 git status 검문소](images/ch24/ch24-f02.png){ width="760" }

그림 24.2 — 커밋 전 git status 검문소
///

목록이 깨끗하면 진행을 승인합니다. 커밋이 완료되면 이런 출력이 나옵니다.

```
[master (root-commit) a1b2c3d] 지도 웹앱 완성: 마커·필터·검색·저장·공유
```

첫 줄의 `a1b2c3d` 같은 문자열은 이 커밋의 해시[^1]로, 커밋마다 붙는 고유한 일련번호입니다. `14 files changed` 숫자는 여러분의 파일 수에 따라 다를 수 있습니다. 중요한 것은 그 목록 어디에도 `.env`가 없다는 점입니다.

!!! tip "팁"
    커밋 직후 `git ls-files | Select-String env` 를 실행해 보면 저장소가 추적 중인 파일 중에 `env`가 들어간 이름이 있는지 한 번 더 확인할 수 있습니다. 아무것도 안 나오면 제대로 된 것입니다. `git ls-files`는 지금 Git 장부에 올라 있는 파일 전체 목록을 보여 주므로, 의심스러울 때마다 꺼내 쓰면 좋습니다.

## 24.3 gh repo create: 한 줄로 깃허브에 올리기

내 컴퓨터 안의 장부는 완성됐습니다. 이제 이 장부를 깃허브라는 클라우드 금고로 올립니다. 5장에서 배운 그 한 줄이면 됩니다. `my-map` 폴더의 터미널에서 실행하세요. Claude Code에게 "이 저장소 깃허브에 public으로 올려 줘"라고 시켜도 같은 명령이 실행됩니다.

```powershell
gh repo create my-map --public --source=. --push
```

이 명령을 다시 한번 뜯어 봅시다. 이번에는 연습이 아니라 실전이니, 옵션 하나하나가 어떤 결정인지까지 짚습니다.

- `my-map` — 깃허브에 만들 저장소 이름입니다. 폴더 이름과 같게 하는 것이 관례입니다. 저장소 주소는 `github.com/여러분의아이디/my-map`이 됩니다.
- `--public` — 누구나 볼 수 있는 공개 저장소로 만듭니다. 공개해도 되는 이유는 8장부터 키를 `.env`에 분리해 두었기 때문입니다. 코드에는 `import.meta.env.VITE_KAKAO_JS_KEY`라는 호출문만 있고 키값 자체는 없습니다. 코드는 공개하되 키는 내 컴퓨터에만 두는 구조가 여기서 효과를 냅니다. 공개로 만드는 실용적인 이유도 두 가지 있습니다. 포트폴리오는 다른 사람이 볼 수 있어야 하고, 25장에서 쓸 GitHub Pages 무료 배포는 공개 저장소에서 제공됩니다.
- `--source=.` — 현재 폴더(`.`)의 저장소를 방금 만든 깃허브 저장소와 연결합니다. 이 연결로 깃허브 쪽 저장소는 `origin`이라는 별명을 얻습니다(5장 복습).
- `--push` — 연결만 하고 끝내지 않고, 지금까지 쌓인 커밋을 즉시 밀어 올립니다.

실행하면 몇 초 안에 이런 출력이 나옵니다.

```
✓ Created repository 여러분의아이디/my-map on GitHub
✓ Added remote https://github.com/여러분의아이디/my-map.git
✓ Pushed commits to https://github.com/여러분의아이디/my-map.git
```

그림 24.4 — gh repo create 실행 결과
///

체크 표시가 세 줄 나오면서 저장소를 만들었고(Created), 연결했고(Added remote), 올렸다고(Pushed) 알려 줍니다. 몇 달의 작업이 클라우드에 올라가는 데 몇 초가 걸렸습니다. 만약 "Name already exists" 오류가 나온다면 예전에 같은 이름의 저장소를 만든 적이 있다는 뜻이니, 이름을 `my-map-app`처럼 바꾸거나 기존 저장소를 정리한 뒤 다시 실행하면 됩니다. 인증 관련 오류가 나온다면 5장에서 배운 `gh auth status`로 로그인 상태부터 확인하세요.

!!! tip "팁"
    `git init`이 만드는 기본 브랜치 이름은 Git 설정에 따라 `master`일 수도, `main`일 수도 있습니다. 어느 쪽이든 `gh repo create --push`는 그대로 올려 주므로 오늘 실습에는 지장이 없습니다. 요즘 깃허브의 표준은 `main`이라서, 통일해 두고 싶다면 푸시 전에 `git branch -M main` 한 줄로 브랜치 이름을 바꿀 수 있습니다. 25장의 배포 워크플로에서 브랜치 이름을 다시 만나게 되니 기억해 두세요.

## 24.4 GitHub 웹에서 확인하기

터미널의 체크 표시를 믿는 것과 내 눈으로 확인하는 것은 다릅니다. 특히 오늘은 "무엇이 올라갔나"만큼 "무엇이 안 올라갔나"가 중요한 날이니, 꼭 웹 화면으로 검수합시다.

```powershell
gh repo view --web
```

## 24.5 커밋 메시지: 나중에 읽을 기록

저장소가 깃허브에 자리 잡았으니, 이제 습관을 이야기하겠습니다. 오늘 이후 여러분은 기능을 고칠 때마다 커밋하고 푸시하게 됩니다. 그때마다 쓰는 커밋 메시지, 대충 지어도 될까요?

몇 달 뒤에 지도가 이상하게 동작해서 커밋 이력을 확인하는 상황을 생각해 봅시다. 이력에 "수정", "수정2", "진짜 마지막", "ㅁㄴㅇㄹ"이라고 적혀 있으면 어느 커밋으로 되돌아가야 할지 알 수 없습니다. 반대로 "카테고리 필터 추가", "말풍선 닫힘 버그 수정", "모바일에서 사이드바 접기"라고 적혀 있으면 문제가 생긴 시점을 좁힐 수 있습니다. 커밋 메시지는 다른 사람에게 보여 주려고 쓰는 것이 아니라, 나중에 자기가 읽으려고 남깁니다.

좋은 메시지의 조건은 거창하지 않고, 아래 세 가지만 지키면 충분합니다.

1. 한 커밋에는 한 가지 일만 담습니다. "필터 추가 + 버그 수정 + 색상 변경"을 한 커밋에 몰아넣으면 되돌리기가 불가능해집니다. 기능 하나가 눈으로 확인될 때마다 커밋합니다. 14장부터 지켜 온 방식입니다.
2. 첫 줄에 요약을 한 문장 씁니다. 무엇을 했는지가 드러나게 쓰고, 한국어로 써도 됩니다.
3. 이유가 필요하면 본문에 덧붙입니다. 남겨 둘 만한 변경이라면 `git commit -m "요약" -m "이유 설명"`처럼 두 번째 `-m`으로 본문을 붙일 수 있습니다.

그리고 커밋 메시지는 AI가 특히 잘 쓰는 글입니다. Claude Code에게 "지금까지 작업 커밋해 줘"라고만 해도, 변경된 파일들을 읽고 알맞은 메시지를 지어서 내놓습니다. 우리는 그 메시지가 실제 작업 내용과 맞는지 읽고 승인하면 됩니다. 메시지가 마음에 안 들면 "메시지는 ~로 바꿔서 커밋해"라고 한마디 얹으면 됩니다.

쌓인 이력을 돌아보는 명령도 하나 챙겨 둡시다. 커밋 한 줄 요약을 시간 역순으로 보여 줍니다.

```powershell
git log --oneline
```

```
f4e5d6c 모바일에서 사이드바 접기
c3b2a1f 마커 클러스터러 적용
...
a1b2c3d 지도 웹앱 완성: 마커·필터·검색·저장·공유
```

![git log --oneline으로 본 커밋 역사](images/ch24/ch24-f07.png){ width="760" }
/// caption
그림 24.7 — git log --oneline으로 본 커밋 역사
///

이 목록이 곧 여러분의 개발 일지가 됩니다. 깃허브 프로필의 기여 그래프에도 커밋한 날마다 초록 칸이 채워집니다.

!!! tip "이렇게 물어보세요"
    > 지금까지 변경된 내용을 커밋하고 푸시해줘. 커밋 메시지는 변경 내용을 보고 네가 한국어로 알맞게 지어서, 커밋하기 전에 나한테 먼저 보여줘.

    앞으로 작업을 마칠 때마다 이 말을 쓰게 됩니다. 5장에서 예고했던 커밋하고 푸시하는 순서가 오늘부터 습관이 됩니다. 이 순서만 지키면 하루 작업이 통째로 날아가는 사고는 겪지 않습니다.

## 24.6 마무리

이번 장에서 `my-map`은 내 컴퓨터 안의 폴더에서 인터넷 주소를 가진 공개 저장소가 되었습니다. `.gitignore`로 `.env`(키가 들어 있어서)와 `node_modules`(다시 만들 수 있어서)를 제외했고, `git init`부터 첫 커밋까지 각 단계에서 확인을 거쳤고, `gh repo create my-map --public --source=. --push` 한 줄로 올린 뒤 웹 화면에서 확인까지 마쳤습니다. 코드는 공개하되 키는 제외한다는 기준은 다른 프로젝트에서도 그대로 적용됩니다.

!!! abstract "이 장의 핵심"
    - 저장소에는 다시 만들 수 있는 파일과 키가 든 파일을 뺀 소스코드만 올립니다. `.env`는 키가 들어 있어서, `node_modules`는 `npm install`로 다시 만들 수 있어서 뺍니다.
    - `.gitignore`는 앞으로의 커밋만 걸러 줍니다. 반드시 `.gitignore` 점검 → 커밋 순서를 지키세요.
    - 커밋 전에 `git status`로 확인합니다. Untracked 목록에 `.env`나 `node_modules`가 보이면 진행하지 않습니다.
    - `gh repo create my-map --public --source=. --push` — 저장소 생성, origin 연결, 푸시까지 한 줄에 끝납니다.
    - 올린 뒤에는 웹에서 검수합니다: `.env` 없음, `node_modules` 없음, 커밋 역사 확인.
    - 커밋 메시지는 미래의 나에게 보내는 쪽지: 한 커밋 한 가지 일, 첫 줄 요약이면 충분합니다.
