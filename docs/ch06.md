# 6장 Orca로 여러 에이전트 다루기

!!! note "이 장에서 배우는 것"
    - 여러 AI 에이전트를 동시에 부리는 도구, Orca가 무엇인지 이해합니다
    - 바이브코딩의 숨은 주역인 git 워크트리(worktree) 개념을 익힙니다
    - Orca 터미널에 Claude Code를 띄우고 작업을 병렬로 돌리는 흐름을 배웁니다
    - 저자가 실제로 쓰는 화면 구성을 보고 나에게 맞는 작업 방식을 정해 봅니다

---

## 6.1 에이전트를 하나만 쓸 때의 한계

4장에서 Claude Code를 설치하고 첫 작업을 시켜 보았습니다. 조금 더 쓰다 보면 한 가지 불편이 생깁니다.

Claude Code에게 일을 시키면, 에이전트가 파일을 읽고 코드를 고치는 동안 우리는 기다립니다. 1~2분짜리 작업이면 괜찮은데, 큰 작업은 5분에서 10분씩 걸리기도 합니다. 그동안은 다른 일을 할 수 없습니다. 그리고 이런 상황도 생깁니다.

- 지도에 마커 찍는 기능을 만드는 동안, 사이드바 디자인도 손보고 싶다
- 에이전트 A에게 기능을 만들게 하고, 에이전트 B에게는 A가 만든 코드를 검토시키고 싶다
- 실험적인 수정을 해 보고 싶은데, 지금 잘 돌아가는 코드는 건드리고 싶지 않다

일을 나눠서 동시에 진행하면 해결됩니다. 에이전트를 하나만 쓸 이유가 없습니다. 여러 에이전트에게 서로 다른 일을 맡기고 각각의 결과를 확인하면 됩니다.

Orca가 이렇게 일할 수 있게 해 줍니다.

Orca는 여러 AI 코딩 에이전트를 작업 공간 단위로 나누어 동시에 실행합니다. 화면 왼쪽에는 작업 목록이 카드 형태로 늘어서 있고, 각 작업을 클릭하면 그 작업 전용 터미널이 열립니다. 이 작업 단위를 워크트리라고 부릅니다. 터미널마다 Claude Code 같은 에이전트를 하나씩 띄워 두고, 카드를 옮겨 다니며 진행 상황을 확인합니다.

## 6.2 워크트리: 작업 공간을 나누는 방법

에이전트를 여러 개 실행하려면 먼저 해결할 문제가 있습니다. 같은 폴더를 여러 에이전트가 함께 고치면 충돌이 생깁니다.

같은 폴더에서 에이전트 두 개가 동시에 일한다고 해 봅시다. A가 `main.js`를 고치는 중인데 B도 `main.js`를 고칩니다. 두 수정이 뒤섞여 파일이 망가집니다. 에이전트마다 폴더를 따로 주어야 합니다.

여기서 3장에서 설치한 git을 다시 씁니다. git의 워크트리(worktree) 기능을 쓰면 하나의 저장소에서 브랜치마다 독립된 폴더를 하나씩 더 만들 수 있습니다.

3장에서 브랜치를 실험용 갈래라고 설명했습니다. 보통 `checkout`으로 브랜치를 바꾸면 같은 폴더의 내용물이 통째로 바뀝니다. 브랜치는 여러 개인데 폴더가 하나뿐이라서 그렇습니다. 워크트리를 쓰면 폴더를 하나 더 만듭니다. `git worktree add`를 한 번 실행하면 같은 저장소를 공유하는 별도의 폴더가 생기고, 그 폴더는 자기만의 브랜치를 가집니다.

```
H:\my-map\               ← 원래 폴더 (main 브랜치)
H:\my-map-feature\       ← 워크트리 1 (feature/marker 브랜치)
H:\my-map-review\        ← 워크트리 2 (review 브랜치)
```

폴더가 세 개이므로 에이전트 세 개가 서로 방해하지 않고 동시에 일할 수 있습니다. 각자 자기 폴더에서 파일을 고치고, 결과가 좋으면 git으로 합치고(merge), 그렇지 않으면 폴더째 지웁니다. 폴더를 통째로 복사하는 것과 달리 워크트리는 저장소의 커밋 기록을 공유하기 때문에 용량을 덜 쓰고 합치기도 쉽습니다.

![워크트리 개념도](images/ch06/ch06-f02.png){ width="760" }

///

!!! tip "워크트리는 두 번째 되돌리기 수단입니다"
    3장에서 커밋을 남겨 두면 이전 시점으로 되돌릴 수 있다고 했습니다. 워크트리는 되돌릴 일 자체를 줄여 줍니다. 에이전트에게 큰 수정을 시킬 때 워크트리에서 하게 하면, 원본 폴더의 잘 동작하는 코드는 처음부터 수정 대상이 아닙니다. 결과가 좋지 않으면 워크트리만 지우면 됩니다.

워크트리가 실제로 어떤 명령인지 확인해 보겠습니다. 외울 필요는 없습니다. Orca가 대신 실행해 주고, 필요하면 에이전트에게 "워크트리 하나 만들어 줘"라고 시켜도 됩니다.

```
git worktree add ..\my-map-feature -b feature/marker
```

이 한 줄을 실행하면 저장소 옆에 `my-map-feature` 폴더가 생기고 거기에 `feature/marker`라는 새 브랜치가 연결됩니다. `git worktree list`를 입력하면 지금 열려 있는 워크트리 목록이 나오고, 다 쓴 워크트리는 `git worktree remove` 명령으로 정리합니다. 워크트리를 다루는 명령은 이 세 개면 됩니다.

다만 워크트리를 직접 관리하려면 명령어를 기억해야 하고, 폴더가 늘어날수록 어느 폴더가 어떤 작업이었는지 확인하기 어려워집니다. Orca가 이 부분을 대신해 줍니다. 버튼 하나로 워크트리를 만들고, 작업마다 카드로 정리하고, 다 쓴 워크트리를 삭제해 줍니다.

## 6.3 Orca 설치하기

Orca는 윈도우에서 동작합니다. 설치 파일과 최신 설치 방법은 공식 사이트에서 확인하세요. 이런 도구는 업데이트가 잦아서 책에 적어 둔 버튼 이름이 몇 달 뒤에 달라질 수 있습니다.

설치 절차의 큰 흐름은 여느 윈도우 앱과 같습니다.

1. 공식 사이트에서 윈도우용 설치 파일을 내려받습니다. 검색창에 "Orca 에이전트"를 넣거나 안내받은 주소로 접속합니다
2. 내려받은 파일을 실행하고 안내에 따라 설치를 마칩니다
3. Orca를 실행한 뒤, 우리가 작업할 프로젝트 폴더(git 저장소)를 엽니다

세부 화면이 책과 조금 다를 수 있습니다. 이 장에서 중요한 것은 버튼의 위치가 아니라 워크트리 카드로 작업을 나누고 카드마다 에이전트를 실행한다는 구조이며, 이 구조는 버전이 바뀌어도 같습니다. 설치 화면이 낯설면 화면을 캡처해서 Claude Code에게 "이 화면에서 뭘 눌러야 해?"라고 물어보아도 됩니다.

## 6.4 터미널에 Claude Code 띄우기

Orca에서는 워크트리 카드 하나가 작업 하나에 대응하고, 카드마다 터미널이 하나씩 붙습니다. 쓰는 순서는 아래와 같습니다.

먼저 작업 카드를 만듭니다. 새 워크트리를 만들면 카드가 하나 생깁니다. 카드에는 "마커 기능 만들기"처럼 작업 이름을 붙입니다. 내부적으로는 git이 새 브랜치와 새 폴더를 만들지만, 화면에서는 카드 한 장이 늘어난 것으로 보입니다. 이름은 나중에 봐도 무슨 작업이었는지 알 수 있게 지어야 합니다. "작업1"이나 "테스트"라고 적어 두면 며칠만 지나도 내용을 알 수 없습니다. "검색기능"이나 "사이드바-디자인"처럼 작업 내용이 드러나게 적으세요.

그다음 카드의 터미널에서 에이전트를 실행합니다. 카드를 열면 그 워크트리 폴더를 기준으로 하는 터미널이 나옵니다. 여기서 4장에서 배운 대로 입력하면 됩니다.

```
claude
```

입력할 것은 이 한 줄뿐입니다. 4장에서 쓰던 Claude Code와 같은 프로그램이 실행되고, 이 카드 전용 폴더 안에서 동작한다는 점만 다릅니다. 에이전트가 어떤 파일을 고치든 이 워크트리 밖으로는 나가지 않습니다. Orca를 쓰기 위해 새로 배울 명령은 없습니다. 4장에서 익힌 대로 권한 프롬프트를 읽고 허용하며, 작게 시키고 확인하는 것도 그대로 적용됩니다.

이제 평소처럼 일을 시킵니다. 프롬프트는 4장에서 배운 맥락·목표·제약·출력 그대로 씁니다.

!!! tip "이렇게 물어보세요"
    > 이 폴더는 카카오지도 웹앱 프로젝트야. 지도에 마커를 찍는 기능을 만들어 줘. 기존 코드 스타일을 따르고, 다 만들면 바꾼 파일 목록을 정리해 줘.

## 6.5 작업을 병렬로 돌리기

이제 카드를 여러 장 만들어 봅시다.

예를 들어 지도 앱을 만들다가 다음과 같은 상황이 되었다고 합시다. 할 일이 세 가지인데, 서로 건드리는 파일이 다릅니다.

| 카드(워크트리) | 맡길 일 | 에이전트 |
|---|---|---|
| `feature-search` | 검색 기능 만들기 | Claude Code |
| `style-sidebar` | 사이드바 디자인 다듬기 | Claude Code |
| `review` | 어제 만든 코드 검토 | codex |

카드 세 장을 만들고, 각 터미널에서 에이전트를 실행하고, 각각 프롬프트를 입력합니다. 그러면 세 작업이 동시에 진행됩니다. 우리가 할 일은 카드를 오가며 진행 상황을 확인하고, 에이전트가 묻는 것(권한 허용, 선택지 결정)에 답하는 것입니다. 가장 크게 달라지는 점은 기다리는 시간이 줄어든다는 것입니다. A가 작업하는 동안 B를 확인하고, B가 작업하는 동안 C에게 다음 일을 시킬 수 있습니다.

어떤 일을 동시에 진행할지 판단하는 기준은 하나입니다. 두 작업이 서로의 결과를 필요로 하는지 확인하면 됩니다. 검색 기능과 사이드바 디자인은 서로의 결과가 필요 없으므로 동시에 진행해도 됩니다. 반면 "마커 찍기"와 "마커를 클릭하면 말풍선 띄우기"는 앞의 결과 위에 뒤의 작업이 쌓이므로 순서대로 시켜야 합니다. 서로 독립적인 일은 동시에, 앞의 결과가 필요한 일은 차례대로 진행합니다.

작업이 끝난 카드는 두 가지 중 하나로 처리합니다. 결과가 좋으면 그 워크트리의 브랜치를 main으로 합칩니다(merge). git이 처리하는 작업이므로 에이전트에게 "이 브랜치 main에 합쳐 줘"라고 시켜도 됩니다. 결과가 좋지 않으면 카드를 지웁니다. 워크트리를 지워도 원본 폴더는 그대로 남습니다.

![카드 세 장이 동시에 굴러가는 모습 (구성 예시)](images/ch06/ch06-f05.png){ width="820" }
/// caption
그림 6.5 — 카드 세 장이 동시에 굴러가는 모습 (구성 예시)
///

!!! warning "병렬은 만능이 아닙니다"
    같은 파일을 고치는 작업 두 개를 동시에 진행하면 안 됩니다. 폴더가 분리되어 있어서 작업 중에는 문제가 없지만, 나중에 두 브랜치를 합칠 때 같은 파일의 같은 부분이 다르게 고쳐져 있으면 git이 어느 쪽을 반영할지 묻는 충돌(conflict)이 발생합니다. 해결할 수는 있지만 처음에는 다루기 어렵습니다. 동시에 진행할 작업은 서로 다른 파일을 건드리는 것으로 고르세요. 그리고 에이전트를 여러 개 실행하면 4장에서 이야기한 요금제 한도도 그만큼 빨리 소모됩니다.

## 6.6 저자의 실전 화면 구성

저자가 이 책과 예제 앱을 만들 때 실제로 쓰는 구성은 다음과 같습니다.

- 모니터 왼쪽 절반: Orca. 워크트리 카드 목록과 터미널. 보통 카드 2~4장이 살아 있습니다. 하나는 지금 만드는 기능, 하나는 검토나 문서 작업, 나머지는 실험용입니다.
- 모니터 오른쪽 절반: 브라우저. 만들고 있는 지도 앱 화면(`localhost:5173`)을 띄워 두고, 에이전트가 "다 했습니다" 하면 바로 새로고침해서 눈으로 확인합니다.
- 정기 순찰. 몇 분에 한 번씩 카드를 훑으며 멈춰 있는 에이전트(질문 대기 중)를 풀어 주고, 끝난 작업은 결과를 확인해서 합치거나 버립니다.

실제 작업의 한 예는 이렇습니다. 카드 1에서는 Claude Code가 지도 앱의 새 기능을 만들고, 카드 2에서는 다른 에이전트가 전날 쓴 원고의 오탈자와 어색한 문장을 검토하고, 카드 3에는 바꿔 볼 만한 수정을 시켜 둡니다. 카드 1 → 2 → 3 순서로 돌아보며 질문에 답하고, 끝난 작업을 합칩니다. 세 카드가 모두 원하지 않는 결과를 내서 전부 지운 날도 있지만, 워크트리에서 작업했으므로 원본 코드에는 영향이 없었습니다.

필요한 것은 복잡한 설정이 아니라 순서입니다. 시키고, 다른 카드를 확인하고, 결과를 검토하고, 합칩니다. 이 순서에 익숙해지면 혼자서도 여러 작업을 동시에 진행할 수 있습니다. 코드를 직접 쓰는 대신 무엇을 시킬지 정하고 결과를 판단하는 일에 시간을 씁니다.

!!! info "더 찾아보기"
