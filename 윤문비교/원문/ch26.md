축하합니다. 여러분의 지도는 이제 인터넷에 살아 있습니다. 25장에서 GitHub Pages 배포가 끝난 순간, 여러분은 "코딩을 배워 보고 싶은 사람"에서 "웹 앱을 만들어 배포한 사람"이 되었습니다. 주소창에 `https://여러분의아이디.github.io/my-map/`을 치면 지구 반대편에서도 여러분의 지도가 열립니다. 스마트폰으로도, 친구의 노트북으로도요.

그런데 한 가지가 빠져 있습니다. 다른 사람에게 리포지토리 링크를 보내면 그 사람 눈에는 `main.js`, `store.js` 같은 파일 목록만 보일 겁니다. 이 코드가 지도 앱이라는 사실도, 무엇을 눌러야 실행되는지도 적혀 있지 않습니다. 이번 장에서는 그 설명을 README로 붙입니다. 그리고 완성된 지도를 공유하는 방법, 여기서 더 진행할 수 있는 다음 단계를 다루고, 마지막으로 0장부터 다룬 내용을 정리하겠습니다. 이 장으로 실습을 마칩니다.

## 26.1 README: 리포지토리의 첫 화면

README는 이름 그대로 나를 읽어 달라는 뜻입니다. 리포지토리 최상위에 `README.md`라는 이름으로 두면, GitHub가 리포 첫 화면에 이 파일을 렌더링해서 보여 줍니다. 방문자는 코드를 열어 보기 전에 이 문서부터 읽는 편입니다. 확장자 `.md`는 마크다운(Markdown)[^1] 형식을 뜻합니다. 이 책의 원고와 Claude Code와 주고받는 대화에서 `#`으로 제목을 달고 `-`로 목록을 만든 문법이 모두 마크다운에 해당합니다.

좋은 README에 정답 공식은 없지만, 개인 프로젝트라면 전 세계 개발자들이 암묵적으로 합의한 4단 구성이 있습니다. 위에서부터 읽는 사람이 궁금해하는 순서를 그대로 따랐습니다.

1. 스크린샷: 이 앱이 무엇인지 화면으로 보여 줍니다. 글로 설명하는 것보다 화면을 보여 주는 편이 빠릅니다. 제목 바로 아래에 둡니다.
2. 기능: "뭘 할 수 있지?"에 대한 답. 목록으로 짧게. 우리 앱은 자랑할 게 열 개도 넘습니다.
3. 기술: "뭘로 만들었지?"에 대한 답. 개발자 방문객이 가장 먼저 훑어보고, 나중에는 여러분의 포트폴리오 구실도 합니다.
4. 실행법: "나도 돌려 볼 수 있나?"에 대한 답. 클론부터 실행까지 명령어를 순서대로. 우리 앱은 카카오 키가 필요하니 `.env` 안내를 꼭 넣어야 합니다.

## 26.2 대표 스크린샷 찍기: ++win+shift+s++

README의 첫인상은 스크린샷이 결정하니, 글보다 사진을 먼저 준비합시다. 윈도우에는 캡처 프로그램을 따로 깔 필요가 없습니다. ++win+shift+s++ 단축키 하나로 해결할 수 있습니다. 누르는 순간 화면이 살짝 어두워지면서 위쪽에 캡처 도구 막대가 나타나고, 마우스로 원하는 영역을 드래그하면 그 부분이 클립보드에 복사됩니다. 캡처 직후 화면 구석에 뜨는 알림을 클릭하면 편집 창이 열려서 자르거나 형광펜을 칠한 뒤 PNG 파일로 저장할 수 있습니다.

찍기 전에 무대를 정돈합시다. 배우가 제일 멋져 보이는 각도를 잡는 겁니다.

- `https://여러분의아이디.github.io/my-map/`으로 배포된 사이트를 엽니다. localhost보다 주소창이 그럴듯해 보입니다.
- 지도를 여러분의 장소가 가장 몰려 있는 동네로 옮기고, 마커·말풍선·사이드바가 한 화면에 어우러지게 확대 레벨을 조절합니다. 말풍선을 하나 열어 두면 화면이 훨씬 생동감 있어 보일 겁니다.
- 개발자도구(++f12++)는 닫습니다. 브라우저 창을 적당히 키우고, 관계없는 탭이나 북마크바가 지저분하면 앱 영역만 드래그해서 담습니다.

!!! warning "주의"
    스크린샷도 공개 리포에 올라가면 누구나 볼 수 있습니다. 지도의 말풍선이나 메모에 집 주소, 실명, 전화번호 같은 개인 정보가 보이지 않는지 캡처 전에 확인하세요. 상세 패널의 메모가 열려 있다면 특히요. 우리 지도는 내가 아는 장소를 모아 둔 것이라 무심코 사생활까지 함께 찍힐 수 있습니다. 그리고 24장에서 말한 것을 한 번 더 짚어 두겠습니다. `.env`의 키는 스크린샷으로도 새어 나갈 수 있으니, 에디터 화면을 찍을 일이 있다면 `.env` 탭이 열려 있지 않은지 보세요.

## 26.3 README 작성: Claude Code에게 시키기

필요한 내용을 정했으니 이제 작성해 보겠습니다. 이번에도 Claude Code에게 시킵니다. Claude Code는 프로젝트 폴더의 코드를 그대로 읽을 수 있으므로, 기능 목록이나 기술 스택을 우리가 알려 줄 필요가 없습니다. 무엇을 어떤 순서로 넣을지만 지시하면 됩니다. 4장에서 배운 프롬프트 4요소 중 출력 형식을 특히 자세히 쓰는 프롬프트라고 할 수 있습니다.

!!! tip "이렇게 물어보세요"
    > 프로젝트 루트에 README.md를 한국어로 만들어줘. 구조는 ①제목과 한 줄 소개와 배포 주소 https://여러분의아이디.github.io/my-map/, ②docs/screenshot.png 스크린샷, ③주요 기능 목록, ④기술 스택, ⑤로컬 실행법 순서로. 실행법은 클론, npm install, .env에 VITE_KAKAO_JS_KEY 설정, npm run dev 순서로 적어줘. 기능과 기술은 src 코드를 직접 읽고 정리해줘. 카카오 JS 키 발급과 플랫폼 도메인 등록이 필요하다는 안내도 실행법에 넣어줘. 실제 키 값은 절대 쓰지 마.

Claude Code가 `src` 폴더를 스캔하더니 README를 만들어 줍니다. 핵심 부분을 함께 읽어 봅시다.

````markdown
# 🗺️ 나만의 지도

카카오지도 위에 내 맛집·카페·여행지를 모으는 나만의 장소 지도입니다.
**바이브코딩**(AI에게 시켜서 만들기)으로 만들었습니다.

👉 **바로 써 보기: https://여러분의아이디.github.io/my-map/**

![나만의 지도 스크린샷](docs/screenshot.png)

## 주요 기능

- 🗺️ 카카오지도 위에 카테고리별 커스텀 마커(🍜맛집/☕카페/🏝여행/💕데이트)
- 💬 마커 클릭 시 커스텀 오버레이 말풍선
- 🔍 키워드 장소 검색 → 내 지도에 바로 추가
- ➕ 지도 클릭으로 장소 추가, ⭐ 별점·메모 편집, 삭제

- 🧭 내 위치 표시, 🔗 URL 해시로 현재 화면 공유

```bash
git clone https://github.com/여러분의아이디/my-map.git
cd my-map
npm install
```

1. [카카오 개발자 콘솔](https://developers.kakao.com)에서 앱을 만들고

2. 앱 설정 → 플랫폼 → Web에 `http://localhost:5173`을 등록합니다.
3. 프로젝트 루트에 `.env` 파일을 만들고 키를 넣습니다.

```
VITE_KAKAO_JS_KEY=여러분의_JS_키
```

4. 개발 서버를 켭니다.

```bash
npm run dev
```
````

## 26.4 만든 앱 공유하기

배포 주소가 있고 README까지 갖췄으니, 이제 자랑해 보겠습니다. 진심으로 하는 말인데, 이 단계를 건너뛰지 마세요. 만든 것을 남에게 보여 주면 두 가지를 얻을 수 있습니다. 하나는 계속할 힘입니다. 네가 만들었냐는 반응 하나가 다음 프로젝트를 시작하게 만듭니다. 다른 하나는 피드백입니다. 사용자는 만든 사람이 생각하지 못한 방식으로 앱을 씁니다. 친구가 무심코 던진 "사진은 못 넣어?" 한마디가 그대로 다음 버전의 기획이 될 수도 있습니다.

자랑의 난이도별 코스를 제안합니다.

- 1단계, 가족이나 친구에게 링크 보내기. 메신저에 배포 주소를 붙여 넣으면 됩니다. 여기서 21장의 URL 공유 기능을 씁니다. 기본 주소가 아니라 `#37.5563,126.9236,5`처럼 특정 위치가 보이는 상태의 링크를 만들어 보내면, 받는 사람도 열자마자 같은 위치를 볼 수 있습니다.
- 2단계, SNS에 올리기. 26.2절에서 찍은 스크린샷에 링크를 함께 올려 보세요. 만드는 과정에서 겪은 문제(회색 지도, 403 오류)와 해결 방법을 함께 적으면 같은 문제를 겪는 사람에게 도움이 될 수 있습니다.
- 3단계, 개발 커뮤니티에 공유하기. GitHub 리포 링크와 함께 개발 커뮤니티나 스터디 모임에 올리면 코드에 대한 피드백까지 받을 수 있습니다. README를 잘 갖춰 놓은 보람이 여기서 나옵니다.

한 가지를 미리 알아 두세요. 링크를 받은 사람의 지도에는 여러분이 저장한 장소가 보이지 않습니다. 17장에서 다룬 대로 장소 데이터가 각자의 브라우저 localStorage에 저장되기 때문입니다. 받은 사람에게는 기본 장소만 있는 지도가 보일 겁니다. 내가 저장한 장소를 함께 보여 주려면 17장의 내보내기 파일을 전달해 가져오기로 읽게 하면 됩니다. 이 제약이 다음 절에서 다룰 다음 단계가 필요한 이유이기도 합니다.

## 26.5 다음 단계 로드맵

이 책의 지도는 완성됐지만, 여러분의 지도는 이제부터 만들어 갈 수 있습니다. 지금 앱의 한계를 정확히 알면 다음에 배울 것이 저절로 정해집니다. 난이도 순으로 네 갈래 길을 소개합니다. 각각이 책 한 권 분량의 세계라서 여기서는 문패만 달아 두지만, 방향을 아는 것과 모르는 것의 차이는 큽니다.

백엔드 저장. 데이터를 브라우저 밖으로 옮기는 길입니다. 지금은 장소가 localStorage에 저장되어 브라우저를 바꾸면 지도가 초기화됩니다. 데이터를 서버의 데이터베이스에 저장하면 어느 기기에서 접속해도 같은 지도를 만납니다. Firebase나 Supabase 같은 서비스형 백엔드(BaaS)[^2]를 쓰면 서버를 직접 운영하지 않고도 시작할 수 있습니다. `store.js`를 만들 때 저장 코드를 `save()` 한 곳에 모아 둔 것이 여기서 도움이 될 수 있습니다. 저장 방식을 바꿀 때 한 곳만 고치면 됩니다.

로그인. 여러 사람이 각자의 지도를 갖게 하는 길입니다. 백엔드가 생기면 자연스럽게 "누구의 데이터인가"라는 질문이 따라옵니다. 카카오 로그인 같은 소셜 로그인을 붙이면 사용자마다 자기 지도를 갖게 되고, 그다음엔 "커플이 함께 쓰는 데이트 지도", "친구들과 공동 편집하는 맛집 지도" 같은 진짜 서비스의 문이 열립니다.

사진 업로드. 별점과 메모에 더해 사진을 넣으면 말풍선에서 보여 줄 수 있는 정보가 늘어납니다. 파일 업로드, 이미지 저장소, 용량과 보안 처리까지 다루어 볼 수 있습니다.

다른 API. 지도 위에 다른 데이터를 얹는 길입니다. 카카오지도 SDK에도 길찾기 연동과 로드뷰, 도형 그리기처럼 우리가 안 쓴 기능이 남아 있고, 세상에는 공공데이터포털의 무료 API가 수천 개 있습니다. 우리 동네 무인 도서 반납함, 전기차 충전소, 미세먼지 측정소… 7장에서 키 발급을, 15장에서 API 호출과 콜백을 이미 겪어 봤으니 여러분은 어떤 API 문서를 만나도 낯이 익을 겁니다.

## 26.6 지금까지 한 일 정리

마지막으로 지금까지의 내용을 정리해 봅시다. 0장에서 이 책은 코드를 직접 치지 않고 AI에게 시켜서 만든다는 방식을 제시했습니다. 그 방식으로 무엇을 만들었는지 순서대로 보면 다음과 같습니다.

1부(1~6장)에서는 개발 환경을 갖췄습니다. Node.js와 Git, Claude Code, GitHub, Orca를 차례로 설치했습니다. 2부(7~10장)에서는 카카오 키를 발급받고 Vite 프로젝트에 첫 지도를 띄웠습니다. 회색 화면과 403 오류도 여기서 다뤘습니다. 3부(11~19장)는 이 책에서 가장 긴 부분이었습니다. 마커, 데이터 설계, 말풍선, 필터, 검색, 추가, 저장, 목록, 상세를 아홉 장에 걸쳐 만들며 상태와 화면을 잇는 구조를 세웠습니다. 4부(20~23장)에서는 내 위치, URL 공유, 클러스터러, 모바일 대응을 추가했고, 5부(24~26장)에서 인터넷에 배포했습니다.

이 과정에서 얻은 것은 지도 앱 하나만이 아닙니다. 세 가지를 반복해서 연습했습니다.

작게 시키기. 1장에서 정한 원칙을 실제로 지켰습니다. "지도 앱 만들어줘"라고 시킨 적은 한 번도 없습니다. "SDK 주소에 clusterer를 추가해줘, 다른 부분은 건드리지 마"처럼 맥락과 목표와 제약을 갖춘 작은 요청을 수십 번 쌓았습니다. 부록 A에 모아 둔 이 책의 프롬프트를 다시 훑어 보면 요청을 쓰는 방식이 눈에 들어옵니다. 이 방식은 AI 도구가 바뀌어도 그대로 쓸 수 있습니다.

읽고 판단하기. 코드를 외우지는 않았지만, AI가 만들어 온 코드를 매번 함께 읽었습니다. `autoload=false`가 왜 필요한지, `subscribe`가 어떻게 화면을 자동 갱신하는지, `escapeHtml`이 무엇을 막는지 확인했습니다. 1장에서 말한 "이해하려 노력하되 외우지 않는다"는 방침 덕분에, AI가 잘못된 코드를 만들어 왔을 때 알아볼 수 있게 됐습니다. 바이브코딩에서 사람이 맡는 일은 타이핑이 아니라 판단 쪽입니다.

되돌리기. git은 3장에서 되돌리기 도구로 소개했고, 책 전체에서 그 역할을 했습니다. 커밋이 있었기 때문에 결과를 모르는 수정도 시도해 볼 수 있었습니다. 결과가 좋지 않으면 되돌릴 수 있습니다. 되돌릴 수 있는 환경에서는 더 많이 시도할 수 있고, 시도한 만큼 빨리 익힙니다.

이 세 가지를 갖추면 만들고 싶은 것을 말로 정리해 AI에게 시키고, 결과를 읽고 판단하고, 잘못되면 되돌리면서 완성까지 진행할 수 있습니다. 이 책의 실습은 여기서 끝나지만, 다음 프로젝트는 빈 폴더에서 시작할 수 있습니다. 만들고 싶은 것이 생기면 터미널을 열고 이렇게 시작하세요. "새 프로젝트를 시작하고 싶어. 계획부터 세워 보자."

즐겁게 만드세요. 그리고 만든 것을 꼭 자랑하세요.
