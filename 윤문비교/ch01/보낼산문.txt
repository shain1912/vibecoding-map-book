[1] 프로그래밍을 배우다 그만둔 이야기는 대체로 비슷합니다. 【1】는 생각으로 검색을 시작하면, HTML을 배워야 하고 CSS를 배워야 하고 자바스크립트를 배워야 하고 API가 무엇인지도 알아야 한다는 글을 만납니다. 그러다 브라우저 탭을 닫으셨을지도 모릅니다. 만들고 싶은 것은 분명한데 배워야 할 것이 너무 많아 보이니, 시작을 미루는 것도 이상한 일은 아닙니다.

[2] 바이브코딩(vibe coding)에서는 배우는 순서가 다릅니다. 문법을 다 배우고 나서 만드는 것이 아니라, 만들고 싶은 것을 말로 설명하면 AI가 코드를 대신 씁니다. 여러분은 결과를 확인하고, 마음에 들지 않으면 다시 말로 고쳐 달라고 하면 됩니다. 【2】, 【3】처럼 한국어 문장으로 요청하면 AI 코딩 도구가 실제로 동작하는 코드를 만들어 줍니다.

[3] 이 말은 2025년 초 AI 연구자 안드레이 카파시(Andrej Karpathy)【4】가 【5】라고 표현한 뒤로 널리 퍼졌습니다. 처음에는 반쯤 농담이었을 겁니다. 지금은 많은 개발자와 비개발자가 이 방식으로 소프트웨어를 만듭니다. 이 책의 원고와 예제 앱도 상당 부분 바이브코딩으로 만들었습니다.

[4] 그림 1.1 — 전통적 코딩과 바이브코딩의 순서 비교

[5] 여기서 흔한 오해 하나를 짚고 넘어가겠습니다. 바이브코딩은 코딩을 배우지 않아도 된다는 뜻이 아닙니다. 배우는 순서와 방법이 다를 뿐입니다. 예전에는 문법을 다 외운 다음에야 무언가를 만들 수 있었지만, 이제는 만들면서 필요한 만큼 이해하면 됩니다. 다만 AI가 만든 코드가 무엇을 하는지, 화면에 뜬 경고가 무슨 뜻인지는 읽을 수 있어야 합니다. 그래야 결과가 이상할 때 어디를 고쳐 달라고 해야 할지 말할 수 있습니다. 이 책에서는 기능을 만들면서 그 읽는 법도 함께 익힙니다.

[6] 이 책에는 코드를 복사해서 붙여 넣는 실습이 없습니다. 긴 코드를 책에서 보고 한 글자씩 따라 치는 실습도 넣지 않았습니다. 실습은 이런 순서로 진행합니다. ① AI에게 보낼 프롬프트를 먼저 보여 주고, ② AI가 만들어 온 코드를 함께 읽고, ③ 그 코드가 왜 그렇게 동작하는지 해설한 뒤, ④ 브라우저에서 결과를 확인합니다. 코드를 입력하는 일은 AI에게 맡깁니다. 결과가 맞는지는 여러분이 판단하면 됩니다.

[7] 바이브코딩이라는 이름 때문에 대충 감으로 한다고 오해하기 쉽습니다. 그러나 잘하는 사람일수록 요청을 명확하게 하고 결과를 꼼꼼히 확인하는 편입니다. 분위기에 맡기는 것은 타이핑이지, 판단까지 맡긴다는 뜻은 아닙니다.

[8] 시중의 많은 입문서는 교육용으로 다듬어 둔 방법을 가르칩니다. 이 책은 조금 다릅니다. 저자가 실제 프로젝트에서 매일 쓰는 작업 흐름을 거의 그대로 따라가 보겠습니다. 도구는 크게 넷으로 나눌 수 있습니다.

[9] 먼저 Claude Code를 씁니다. 터미널에서 실행하는 AI 코딩 에이전트로, 이 책에서 가장 많이 다루는 도구입니다. 코드 조각을 답해 주는 데서 그치지 않습니다. 프로젝트 폴더 안에서 파일을 만들고 고치며, 명령어를 실행하고, 에러를 읽어 스스로 수정하기도 합니다. 【6】라고 요청하면 어떤 파일을 어떻게 바꿀지 계획을 세운 뒤 실제로 바꿔 놓습니다.

[10] Git은 코드의 변경 이력을 기록해 두었다가 이전 시점으로 되돌려 줍니다. AI가 코드를 대신 쓰는 작업에서는 이 도구가 특히 중요합니다. AI가 고친 결과가 마음에 들지 않으면 마지막으로 잘 동작하던 시점으로 돌아가야 합니다. 기록이 없으면 돌아갈 수가 없습니다. 이 내용은 3장에서 자세히 다루겠습니다.

[11] GitHub CLI는 만든 코드를 인터넷 저장소인 GitHub에 올리고 관리해 줍니다. 터미널에서 【7】 명령으로 실행합니다. 브라우저에서 버튼을 찾아 누르는 대신 명령어 한 줄로 저장소를 만들 수 있으니 AI 에이전트에게 시키기에도 좋습니다.

[12] Orca는 여러 AI 에이전트를 한 화면에 띄워 놓고 함께 다루는 데스크톱 앱입니다. 한 에이전트에게 기능 A를 시켜 놓고, 기다리는 동안 다른 에이전트에게 기능 B를 시킬 수 있습니다. 처음에는 없어도 되지만, 익숙해지면 기다리는 시간이 줄어듭니다.

[13] 그림 1.2 — 저자의 바이브코딩 워크플로 한눈에 보기

[14] 네 도구를 함께 쓰는 하루는 이렇게 흘러갑니다. 아침에 Orca를 켜고 Claude Code에게 【8】라고 시켜 둡니다. 에이전트가 코드를 고치는 동안 다른 일을 하다가 돌아와 브라우저로 결과를 확인합니다. 결과가 맞으면 Git으로 커밋하고 GitHub에 올리면 되겠지요. 맞지 않으면 【9】라고 다시 시키거나, 되돌린 뒤 요청을 다르게 써 볼 수도 있습니다. 코드를 직접 입력하지 않는 날도 많지만, 그렇다고 사람이 할 일이 없어지는 것은 아닙니다. 무엇을 만들지 정하고 결과가 맞는지 판단하는 일은 여전히 사람 몫입니다.

[15] 이 책의 1부(2~6장)에서는 이 작업 흐름을 여러분의 윈도우 PC에 그대로 갖춥니다.

[16] AI가 코드를 다 써 준다면 우리는 무엇을 배워야 할까요? 이 책에서는 이해하려 노력하되 외우지는 않는 쪽을 택하겠습니다.

[17] 외우지 않아도 되는 것부터 말씀드리겠습니다. 함수 이름의 정확한 철자, 괄호와 세미콜론의 위치, API 옵션의 나열 순서가 그렇습니다. 예전에는 프로그래밍을 배울 때 여기에 시간을 가장 많이 썼지만, 이제는 AI가 사람보다 훨씬 정확하게 기억합니다. 카카오지도에서 마커를 만드는 클래스 이름이 【10】인지 【11】인지 헷갈려도 괜찮습니다. AI에게 물어보면 됩니다.

[18] 반대로 구조와 흐름은 이해해야 합니다. 예를 들어 보겠습니다. 【12】 【13】 【14】 이런 질문에 대략이라도 답할 수 있으면 AI가 만든 코드가 이상할 때 알아챌 수 있습니다. 무엇을 고쳐 달라고 해야 할지도 정확히 말할 수 있습니다.

[19] 여러분은 무엇을 만들지 정하고 결과가 맞는지 확인합니다. 코드를 한 줄씩 직접 쓸 줄은 몰라도 되지만, 파일이 몇 개이고 데이터가 어디에 저장되며 어떤 순서로 실행되는지는 읽을 수 있어야 합니다. 그래야 AI가 요청한 기능을 빠뜨리거나 엉뚱하게 만들었을 때 알아챌 수 있습니다. 그래서 이 책에는 코드 해설이 길지 않으면서도 꼬박꼬박 들어 있습니다. 코드는 구조를 확인하려고 읽습니다.

[20] 그림 1.3 — 외울 것과 이해할 것

[21] 그래서 이 책의 실습에는 설명을 요청하는 프롬프트가 자주 나옵니다. AI에게 일을 시킨 다음 이렇게 한 번 더 물어보면 좋습니다.

[22] AI는 코드를 만들어 줄 뿐 아니라 그 코드를 설명해 주기도 합니다. 같은 질문을 여러 번 해도 괜찮습니다. 모르는 것을 모른다고 편하게 말할 수 있다는 점은 혼자 공부할 때 특히 도움이 될 겁니다.

[23] AI 에이전트는 유능하지만 실수도 합니다. 틀린 코드를 자신 있게 내놓기도 하고, 시키지 않은 것까지 고쳐 놓기도 합니다. 그래서 일을 시킬 때 몇 가지 요령을 알아 두면 좋습니다. 이 책 전체에서 지킬 세 가지로 정리했습니다.

[24] 작게 시킵니다. 【15】라고 시키면 AI는 무언가를 만들어 내겠지만, 한 번에 너무 많은 코드가 나와서 어디가 잘못됐는지 확인하기 어려울 겁니다. 대신 【16】 → 【17】 → 【18】처럼 한 번에 하나씩 시켜 보세요. 요청이 작으면 결과를 바로 확인할 수 있고, 잘못됐을 때 원인을 찾을 범위도 좁아집니다. 이 책의 26개 장도 같은 순서로 구성했습니다.

[25] 결과를 확인합니다. AI가 다 했다고 말했다고 해서 실제로 동작한다는 뜻은 아닙니다. 요청 하나가 끝날 때마다 브라우저를 새로고침해 화면을 보고, 개발자 도구의 콘솔에 빨간 에러가 없는지 살펴보세요. 확인하지 않고 다음 요청을 이어 가면 나중에 문제가 생겼을 때 어느 요청에서 잘못됐는지 찾기 어렵습니다. 요청 하나마다 확인을 한 번씩 하는 편이 낫습니다.

[26] 결과가 이상하면 되돌립니다. 그 위에 수정 요청을 덧대기보다, 이전 상태로 돌아가 요청을 다시 쓰는 편이 빠를 때가 많습니다. Git으로 잘 동작하던 시점을 저장해 두었다면 명령어 한 줄로 되돌릴 수 있습니다. 되돌릴 수 있으면 결과를 모르는 요청도 해 볼 수 있고, 그만큼 여러 방법을 시험해 볼 수 있습니다.

[27] 그림 1.4 — 바이브코딩 3원칙: 작게 시키기 · 확인하기 · 되돌리기

[28] AI가 만든 코드를 확인 없이 계속 쌓아 올리다가 일이 꼬이는 경우가 가장 많습니다. 특히 【19】 식의 큰 요청 뒤에는 반드시 동작을 확인하고, 잘 되는 시점을 Git으로 저장해 두세요. 저장하지 않은 채 다음 요청을 이어 가면 되돌아갈 지점이 없어집니다.

[29] 이 원칙은 4장에서 배울 프롬프트의 네 요소와 함께 책 전체에서 계속 씁니다. 네 요소란 맥락, 목표, 제약, 출력 형식을 말합니다. 도구는 몇 년 뒤에 바뀔 수도 있겠지만, 에이전트에게 일을 시키는 방식은 어떤 도구를 쓰든 크게 다르지 않을 겁니다.

[30] 이제 다음 장부터 하나씩 설치할 도구를 미리 소개하겠습니다. 각 도구가 왜 필요한지만 알아 두어도 설치 과정이 한결 덜 지루할 겁니다.

[31] 그림 1.5 — 도구 5종의 역할 지도

[32] ① Node.js (2장). 자바스크립트를 브라우저 밖에서도 실행해 주는 프로그램입니다. 우리가 쓸 개발 서버 Vite와 Claude Code가 모두 Node.js 위에서 돌기 때문에 가장 먼저 설치합니다. 나머지 도구를 쓰려면 Node.js부터 있어야 합니다.

[33] ② Git (3장). 앞에서 이야기한 되돌리기 도구입니다. 프로젝트의 상태를 시점별로 저장(커밋)해 두었다가 언제든 그 시점으로 돌아갈 수 있습니다. 지도를 띄우기 전에 반드시 먼저 설치합니다.

[34] ③ Claude Code (4장). 이 책에서 가장 많이 쓰는 AI 코딩 에이전트입니다. 터미널에서 실행하며, 한국어로 시키면 파일을 만들고 고치고 실행까지 해 줍니다. Claude Pro 유료 구독이 필요하지만, 4장에서 무료로 쓸 수 있는 도구도 함께 소개하겠습니다.

[35] ④ GitHub CLI (5장). 코드를 인터넷 저장소 GitHub에 올리는 명령줄 도구입니다. 25장에서 우리 지도 앱을 GitHub Pages로 공개할 때 이 도구를 씁니다.

[36] ⑤ Orca (6장). 여러 에이전트를 나란히 지휘하는 데스크톱 앱입니다. 다섯 가지 중 이 도구만은 없어도 책을 끝까지 따라갈 수 있습니다. 다만 설치하면 저자가 실제로 쓰는 작업 방식을 그대로 따라 해 볼 수 있습니다.

[37] 여기에 도구는 아니지만 재료가 하나 더 필요합니다. 카카오지도 API 키(7장)입니다. 카카오가 제공하는 지도 데이터를 우리 앱에서 쓰려면 이 인증 키가 필요한데, 무료로 발급받을 수 있습니다. 도구 5종을 설치하고 키까지 받으면 8장부터 지도를 띄웁니다.

[38] 설치 장(2~6장)에서 도구 버전이 책의 화면과 조금 달라도 괜찮습니다. 도구는 자주 바뀌지만 설치 순서는 같습니다. 화면이 많이 다르면 그 화면을 캡처해서 AI에게 【20】라고 물어보면 됩니다.
