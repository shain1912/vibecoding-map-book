[34] 설치 확인 절차가 끝났으면, 이제 두 줄의 간단한 기본 설정을 진행하도록 하겠습니다. git은 작업 내용을 커밋으로 저장할 때마다 【17】 정보를 함께 기록하도록 되어 있습니다. 따라서 사용하는 사람의 이름과 이메일 주소를 미리 등록하여 주어야 합니다. 터미널에 아래 두 줄의 명령어를 한 줄씩 차례로 입력하도록 하십시오. 따옴표로 표시된 부분은 본인의 실제 이름과 이메일 주소로 변경하여 입력하여야 합니다.
[35] 명령어 끝에 【18】 옵션을 추가하면, 현재 사용 중인 컴퓨터의 모든 프로젝트에서 동일한 설정이 적용됩니다. 이 설정은 한 번만 수행하면 이후 어떤 프로젝트 폴더에서 작업하더라도 별도로 입력할 필요가 없습니다. 이름의 경우 한글, 영문, 닉네임 어느 것을 사용하여도 무방합니다. 다만 이메일 주소의 경우, 5장에서 생성하게 될 GitHub 계정에 등록할 이메일 주소와 동일하게 설정할 것을 권장합니다. 그렇게 하면 이후 GitHub에 업로드한 작업 기록이 본인의 계정 활동 내역으로 정상적으로 인식되기 때문입니다.
[36] 위 두 줄의 명령어를 실행하여도 터미널 상에는 별도의 출력 내용이 나타나지 않을 것입니다. 해당 명령어는 원래 정상적으로 처리되더라도 아무런 메시지를 반환하지 않도록 설계되어 있습니다. 만약 설정이 정상적으로 저장되었는지 확인하고 싶다면, 아래의 명령어를 입력하여 확인할 수 있습니다.
[37] 그림 3.6 — user.name과 user.email이 정상적으로 등록된 모습
[38] 확인 목록에서 【19】와 【20】 항목이 본인이 입력한 내용과 일치하게 표시된다면 설정은 완료된 것입니다. 만약 입력 과정에서 오타가 발생하였다고 하여도, 동일한 명령어를 다시 실행하면 새롭게 입력한 내용으로 덮어쓰여지므로 걱정할 필요가 없습니다. git은 이 설정 내용을 컴퓨터 내부에 별도의 파일로 저장하고 관리하므로, 이 두 줄의 명령어는 이 책 전체를 통틀어 단 한 번만 입력하면 충분합니다.
[39] 만약 자신의 이메일 주소를 공개하고 싶지 않은 경우, GitHub에서 제공하는 비공개용 대체 이메일 주소를 사용하면 됩니다. GitHub는 실제 이메일 주소 대신 사용할 수 있는 주소를 【21】 형식으로 발급하여 주고 있습니다. 따라서 5장에서 GitHub 계정을 생성한 뒤 해당 대체 주소로 변경하여 등록하여도 무방합니다.
[40] git에서 사용할 수 있는 명령어는 수십 가지가 넘지만, 이 책에서 별도로 암기하여야 할 명령어는 사실상 없습니다. 4장에서 Claude Code를 설치하고 나면, 대부분의 git 관련 작업을 명령어 대신 자연어로 요청하여 처리할 수 있기 때문입니다. 그렇지만 git의 핵심 개념 세 가지만은 반드시 이해하고 넘어가도록 하여야 합니다. AI에게 작업을 요청할 때에도, 그리고 AI가 수행한 작업 내용을 확인할 때에도 이 세 가지 개념이 계속해서 등장하기 때문입니다.
[41] 그림 3.7 — 저장소, 커밋, 브랜치 개념 설명도
[42] 저장소(repository)란 git이 프로젝트의 변경 이력을 관리하는 프로젝트 폴더 자체를 의미합니다. 일반적인 폴더에서 【22】 명령어를 실행하면 해당 폴더 내부에 【23】이라는 이름의 숨김 폴더가 생성되며, 그 시점부터 해당 폴더는 git의 관리 대상인 저장소가 됩니다. 겉으로 보기에는 여전히 일반적인 폴더와 동일하지만, 내부의 【24】 폴더에 변경 이력이 차곡차곡 기록되기 시작하는 것입니다.
[43] 커밋(commit)이란 현재 시점의 폴더 전체 상태를 파일 단위로 기록하는 작업을 의미하며, 그렇게 기록된 단위 하나하나를 가리켜 커밋이라고 부르기도 합니다. 커밋을 생성할 때는 작업 시각, 앞서 등록한 사용자의 이름과 이메일 주소, 그리고 어떤 내용을 변경하였는지에 대한 간략한 설명을 함께 저장하게 됩니다. 이때 함께 작성하는 설명을 커밋 메시지라고 하며, 메시지는 【25】과 같은 형식으로 작성하는 것이 일반적입니다. 이렇게 커밋이 쌓이면 프로젝트의 전체 변경 이력이 되며, 언제든지 이력 상의 특정 시점으로 작업 내용을 복원할 수 있게 됩니다. 앞서 3.1절에서 설명한 작업 복원 기능이 바로 이 커밋을 기반으로 작동하는 것입니다.
[44] 커밋 메시지를 작성하는 요령에 관하여도 미리 알아 두도록 하십시오. 나중에 다시 확인하여도 무엇을 저장한 시점인지 명확하게 파악할 수 있도록 작성하여야 합니다. 즉, 【26】이나 【27】과 같이 모호하게 작성하는 대신, 【28】과 같이 구체적으로 어떤 내용이 변경되었는지를 명시하는 것이 좋습니다. 물론 이 책에서 다루는 바이브코딩 환경에서는 커밋 메시지조차 AI가 대신 작성하여 주는 경우가 많습니다. 그러나 AI가 작성한 메시지가 적절한 내용인지 판단하는 것은 사용자 본인이므로, 메시지는 구체적이고 명확할수록 이후 원하는 시점으로 복원하기에 용이하다는 점을 기억하여 두시기 바랍니다.
[45] 브랜치(branch)란 기존의 작업 내용에 영향을 주지 않으면서 새로운 시도를 할 수 있도록 하여 주는 기능입니다. 마치 나무의 줄기에서 새로운 가지가 뻗어 나가듯, 기존의 작업 흐름에서 갈래를 하나 분리시켜 그곳에서만 독립적으로 작업을 진행할 수 있게 하는 방식입니다. 예를 들어 현재 적용된 디자인은 그대로 유지한 채 지도 화면을 다크 모드로 변경하는 작업을 시도하여 보고 싶다면, 새로운 브랜치를 생성한 뒤 그곳에서 작업을 진행하면 됩니다. 작업 결과가 만족스럽다면 기존의 작업 흐름에 통합하고, 그렇지 않다면 그냥 삭제하여 버리면 되므로 원래의 작업 내용은 전혀 변경되지 않고 보존됩니다. 이 책의 실습 내용은 대부분 【29】이라는 이름의 기본 브랜치 하나만을 사용하여 진행하게 될 것이므로, 지금은 이러한 기능이 존재한다는 사실만 알아두면 충분합니다. 6장에서 다룰 Orca의 워크트리 기능 역시 이 브랜치 개념을 기반으로 구성되어 있으며, 여러 AI 에이전트에게 동시에 작업을 분담시킬 수 있는 것도 바로 이 브랜치 기능을 이용하기 때문입니다.
[46] 세 가지 핵심 개념의 관계는 다음과 같이 정리할 수 있습니다. 즉, 저장소에 변경 내용을 커밋으로 기록해 두고, 결과를 예측하기 어려운 변경 사항에 대하여는 브랜치를 별도로 생성하여 작업하는 것입니다. 설령 AI가 코드를 예상과 다르게 변경하였다고 하여도, 미리 커밋을 생성하여 두었다면 언제든지 작업 시작 전의 상태로 복원할 수 있습니다.
[47] Claude Code를 설치하고 나면, 작업 내용을 이전 상태로 복원하는 작업 역시 아래의 예시와 같이 자연어로 요청하여 처리할 수 있게 됩니다. 따라서 복잡한 명령어를 별도로 암기할 필요가 없습니다.
[48] 아래의 두 번째 예시 문장이 바로 이 장에서 설명한 작업 복원에 관한 요청입니다. 이 요청이 정상적으로 작동하기 위해서는, 첫 번째 예시 요청과 같이 평소에 작업 내용을 주기적으로 커밋으로 저장하여 두어야 한다는 점을 명심하여야 합니다.
