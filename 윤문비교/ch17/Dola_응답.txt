[3] 그림 17.1 — 새로고침 전(왼쪽)과 후(오른쪽): 추가한 장소가 사라진 모습
[4] 이제 원인을 파악해 보겠습니다. 현재 장소 데이터는 【1】 내의 【2】라는 변수에 배열 형태로 저장되어 있습니다. 16장에서 【3】를 호출하면 이 배열에 새로운 장소가 【4】되고 화면에 마커가 표시되었습니다. 이 부분까지는 정상적으로 작동합니다. 문제는 이 변수가 저장되는 위치에 있습니다.
[5] 자바스크립트의 변수는 컴퓨터의 메모리에 저장됩니다. 메모리는 접근 속도가 매우 빠르지만 전원이 꺼지거나 프로그램이 종료되면 내용이 완전히 삭제됩니다. 브라우저에서 프로그램이 종료되는 시점은 바로 새로고침을 실행할 때입니다. 새로고침은 페이지를 단순히 수정하는 것이 아닙니다. 실행 중이던 자바스크립트 코드를 모두 내리고 처음부터 다시 실행하는 과정입니다. 【5】 배열도 함께 사라지고, 새로 로드된 환경에서는 【6】의 기본 데이터를 기준으로 다시 시작하게 됩니다. 우리가 추가한 장소를 별도의 장소에 기록해 두지 않았으므로 복원할 수 없습니다.
[6] 메모리는 프로그램이 실행 중일 때만 데이터를 보관하는 공간입니다. 읽고 쓰는 속도는 빠르지만, 페이지를 새로고침하면 그 안에 저장된 값이 모두 사라집니다. 새로고침 이후에도 유지되어야 하는 값이라면 별도의 장소에 기록해 두어야 합니다. 이처럼 프로그램이 종료되어도 데이터를 보관하는 저장 공간을 영속 저장소【7】라고 부릅니다. 브라우저는 웹사이트별로 이러한 저장 공간을 하나씩 제공하며, 그 이름이 바로 localStorage입니다.
[7] 그림 17.2 — 메모리와 localStorage의 차이점
[8] localStorage는 브라우저가 사이트별로 하나씩 할당하는 키-값 형식의 저장소입니다. 키에 이름을 지정하여 값을 저장하고, 나중에 동일한 키를 사용하여 값을 불러올 수 있습니다. 사용 방법은 매우 간단합니다. 직접 확인하는 것이 가장 좋으니, 개발자도구 콘솔(++f12++)에서 직접 실습하여 보시기 바랍니다.
[9] 이제 중요한 실험을 진행해 보겠습니다. 새로고침을 실행한 다음 콘솔에 동일한 명령어를 다시 입력하여 보시기 바랍니다.
[10] 값이 그대로 유지되는 것을 확인할 수 있습니다. 브라우저를 완전히 종료하였다가 다시 실행하여도, 다음 날 접속하여도 값은 그대로 보존될 것입니다. 변수와의 차이점이 바로 이 부분입니다. 개발자도구의 Application 탭 → Local Storage → http://localhost:5173 경로를 열면 방금 저장한 키와 값을 직접 확인할 수 있습니다. 한국어 버전 크롬에서는 탭 이름이 「애플리케이션」으로 표시됩니다. 탭 목록에 해당 항목이 보이지 않는 경우 개발자도구 오른쪽 끝에 위치한 【8】 버튼을 클릭하여 보시기 바랍니다. 앞으로 저장된 값을 확인할 때 이 화면을 자주 사용하게 될 것이므로 위치를 기억해 두시기 바랍니다.
[11] 그림 17.3 — 개발자도구 Application 탭에서 확인한 localStorage
[12] localStorage의 주요 특징을 자세히 알아보겠습니다.
[13] 마지막 사항에 관하여는 다음 절에서 해결하겠습니다. 우리가 사용하는 【9】에는 문자열이 아닌 객체가 배열 형태로 저장되어 있습니다. 배열을 그대로 저장하면 어떻게 되는지 콘솔에서 확인하여 보시기 바랍니다.
[14] 배열이 【10】이라는 문자열 형식으로 변환되어 저장됩니다. 저장하는 시점에 자바스크립트가 배열을 문자열로 자동 변환하기 때문이며, 이 과정에서 배열의 구조 정보가 손실됩니다. 객체의 경우 더욱 심각하여 【11】이라는 문자만 저장됩니다. localStorage에는 문자열 데이터만 저장할 수 있는 반면, 우리가 저장하려는 데이터는 배열과 객체 형식입니다. 따라서 구조를 유지한 채 문자열로 변환하는 방법이 필요합니다.
[15] 이러한 변환 과정을 JSON 직렬화라고 부릅니다. 12장에서 장소 데이터 구조를 설계할 때 JSON 형식을 간략하게 언급하였으나, 이번 장에서 자세히 활용하여 보겠습니다. 자바스크립트에서는 이러한 변환 작업을 위한 내장 도구를 두 가지 제공하고 있습니다.
[16] 콘솔에서 변환과 복원 과정을 직접 실습하여 보시기 바랍니다.
[17] 【12】가 생성한 결과값은 원본과 유사해 보이지만 실제로는 문자열 형식입니다. 배열과 객체의 구조 정보(중괄호, 대괄호, 따옴표)를 모두 문자열로 변환하여 보관하므로, 【13】가 해당 문자열을 읽어 원래의 배열과 객체 형식으로 완벽하게 복원할 수 있습니다. 데이터의 값이 하나도 손실되지 않는다는 점이 매우 중요합니다. 데이터 변환(【14】) → 저장(【15】) → 읽기(【16】) → 복원(【17】)의 네 단계를 거치면 어떤 형식의 데이터라도 새로고침 이후에도 유지할 수 있습니다.
[18] 그림 17.4 — 직렬화 및 복원 처리 과정
[19] 【18】는 문법 검사 기준이 매우 엄격합니다. 따옴표 하나만 누락되어도 JSON 문법 규칙에 위배되어 에러를 발생시키고 작업을 중단합니다. 문제가 있는 데이터를 그대로 반환하는 것보다 에러를 알리는 것이 더 적절하다고 판단하기 때문입니다. 따라서 에러 발생에 대비하는 코드를 함께 작성하여야 하며, 이 작업은 다음 절에서 설명하는 try-catch 구문이 처리할 것입니다.
[20] 기본적인 원리는 모두 설명하였습니다. 이제 이 내용을 우리의 【19】에 적용하여 보겠습니다. 구현에 필요한 요구사항을 정리한 다음 Claude Code에게 전체적인 구현을 요청하여 보겠습니다.
[21] 프롬프트에 포함된 설계 원칙은 세 가지입니다. 키 이름을 별도로 정의하고, 저장 로직을 save() 함수 하나에 통합하며, try-catch 구문을 적용하는 것입니다. 이러한 세부 원칙까지 인공지능이 자동으로 판단하여 적용하지는 않으므로, 우리가 직접 규칙을 정하고 명시하여야 합니다. 먼저 Claude Code가 수정한 【20】 파일의 앞부분, 즉 데이터 불러오기와 저장 기능을 담당하는 코드부터 확인하여 보겠습니다.
[22] 16장에서는 【21】였던 첫 번째 코드 라인이 【22】로 변경되었습니다. 이제 앱은 실행 시점에 기본 데이터 대신 저장된 데이터부터 우선적으로 불러오도록 동작합니다. 차례로 해당 내용을 자세히 살펴보겠습니다.
[23] 【23】에서는 localStorage에 데이터를 저장할 때 사용할 키 이름을 상수로 미리 정의하였습니다. 【24】와 같이 일반적인 이름 대신 앱 이름을 포함한 키를 사용하면, 다른 코드에서 사용하는 키 이름과 충돌하는 문제를 방지할 수 있습니다. 키 이름 끝에 추가한 【25】는 버전을 나타내는 표시입니다. 추후 데이터 구조를 크게 변경하는 경우 【26】와 같이 새로운 키 이름을 사용하여, 구 버전 형식으로 저장된 데이터를 신 버전 코드가 잘못 읽는 상황을 예방할 수 있습니다.
[24] 【27】는 앱이 시작될 때 한 번만 실행되는 함수입니다. 【28】를 통하여 localStorage에서 저장된 값을 불러오고, 【29】를 통하여 원래의 배열과 객체 형식으로 복원합니다. 이는 그림 17.4에 표시된 데이터 불러오기 경로에 해당합니다. 앱에 처음 접속하는 사용자로서 저장된 데이터가 전혀 없는 경우, 【30】의 반환값이 【31】이 되므로 【32】 조건문을 통과하지 못하고 기본 데이터를 기준으로 앱을 시작하게 됩니다. 데이터를 복원한 이후에는 두 가지 추가 검사를 진행합니다. 【33】를 사용하여 불러온 데이터가 배열 형식이 맞는지 확인하고, 배열이 맞는 경우 【34】를 사용하여 각 항목의 유효성을 차례로 검사합니다. 이 과정에서 사용되는 【35】 함수의 역할과 구현 내용은 잠시 후에 자세히 설명하겠습니다.
[25] try-catch 구문에 관하여 설명하여 드리겠습니다. 【36】는 우선 코드를 실행해 보고, 실행 도중 에러가 발생하면 catch 블록에서 해당 문제를 처리하라는 의미입니다. try 블록 내에서 에러가 발생하면 프로그램이 종료되지 않고 catch 블록으로 이동하여 처리 절차를 이어가게 됩니다. 해당 위치에서 발생할 수 있는 문제는 가상의 상황이 아닌 실제로 발생할 수 있는 상황입니다. 사용자가 개발자도구에서 저장된 값을 임의로 수정하여 JSON 형식이 훼손된 경우, 【37】가 에러를 발생시킵니다. 또한 브라우저의 사생활 보호 모드나 쿠키 및 사이트 데이터 차단 설정이 활성화된 경우, 【38】에 접근하는 것 자체가 에러를 유발할 수 있습니다. 이러한 안전 장치를 마련해 두지 않으면, 해당 환경의 사용자는 앱이 하얀 화면만 보여준 채 정상적으로 작동하지 않는 문제가 발생합니다. 안전 장치를 마련해 두면, 저장 기능이 정상적으로 작동하지 않더라도 앱의 나머지 기능은 계속 사용할 수 있습니다. 저장 기능이 주요 기능이 아닌 보조 기능에 해당하는 경우, 저장에 실패하더라도 앱 자체는 정상적으로 작동하도록 설계하는 것이 바람직합니다.
[26] 【39】는 불러온 데이터의 유효성을 검사하고 정상화하는 함수입니다. try-catch 구문이 JSON 형식 자체가 훼손된 심각한 오류를 처리한다면, normalize 함수는 그 다음 단계의 문제를 처리하는 역할을 수행합니다. 【40】가 정상적으로 완료되었다고 하여도 데이터의 내용까지 정상적이라고 단정할 수는 없습니다. 문법적으로는 올바른 JSON 형식이지만 내용에 문제가 있는 경우가 존재할 수 있기 때문입니다. 예를 들어 장소 이름이 누락되었거나, 위도 값이 999로 비정상적이거나, 별점이 -3으로 표시된 데이터가 포함될 수 있습니다. 이러한 문제는 사용자가 개발자도구에서 값을 임의로 수정한 경우, 구 버전 앱에서 저장된 데이터를 불러온 경우, 또는 17.5절에서 설명하는 가져오기 기능을 통하여 외부 파일로부터 불러온 데이터인 경우 발생할 수 있습니다. 따라서 store는 어디에서 유래한 데이터라 하더라도 화면에 표시하기 전에 반드시 이 함수를 통과시켜 검사하고 정리합니다. 【41】 위치에서 해당 함수의 구현 내용을 확인할 수 있습니다.

[41] 이러한 제한 사항이 있으므로 실제 서비스에서는 데이터를 별도의 서버에 보관하는 방식을 사용합니다. 다만 서버와 데이터베이스에 관한 내용은 이 책의 범위를 벗어나므로 여기서 다루지 않겠습니다. 26장에서 다음 단계로서 간략하게 소개하여 드릴 예정입니다. 그 대신 우리는 별도의 파일 형식으로 데이터를 백업하는 방법을 구현하겠습니다. 전체 장소 데이터를 JSON 파일로 내보내는 기능과, 저장된 JSON 파일을 다시 불러오는 기능을 추가할 것입니다. 파일 형식으로 데이터를 저장해 두면 안전하게 백업할 수 있을 뿐만 아니라, 다른 컴퓨터로 데이터를 옮겨 사용하거나 다른 사람에게 전달하는 것도 가능해집니다.
[42] 먼저 【92】에 추가된 두 가지 메서드를 확인하여 보겠습니다.
[43] 【93】의 【94】 메서드에 이전에 보지 못했던 세 번째 인자가 추가되었습니다. 세 번째 인자 【95】는 【96】 옵션에 해당하는 매개변수입니다. localStorage에 데이터를 저장할 때는 사람이 직접 열어서 확인할 경우가 많지 않으므로, 불필요한 공백을 제거하여 파일 크기를 최소화한 상태로 저장하였습니다. 반면 내보내기 기능을 통하여 생성하는 파일은 사용자가 직접 열어서 확인할 수 있으므로, 가독성이 좋도록 적절한 줄 바꿈과 들여쓰기를 추가하여 저장하는 것이 합리적입니다.
[44] 【97】 메서드는 외부로부터 불러온 파일의 내용을 그대로 신뢰하지 않고 철저하게 검사합니다. 불러온 내용을 JSON 형식으로 변환한 뒤 데이터가 배열 형식이 맞는지 확인하고, 17.4절에서 구현한 정규화 함수 【98】에 모든 항목을 통과시켜 유효성을 검사하고 데이터를 보정합니다. 동일한 검사 로직을 중복하여 작성하지 않고 기존에 작성한 함수를 재사용하였다는 점에 주목하여 주시기 바랍니다. 장소 이름과 좌표의 유효성 검사부터 별점 값의 범위 보정, 식별자의 유효성 검사까지 모든 검사 작업을 한 번에 수행할 수 있습니다. 다만 데이터를 처리하는 방식에 있어서는 【99】보다 더 엄격한 기준을 적용합니다. 【100】는 문제가 있는 데이터 항목은 제외하고 정상적인 데이터만을 사용하여 작업을 계속 진행하는 방식인 반면, 【101】는 데이터 검사 과정에서 문제가 발견되면 【102】를 통하여 해당 항목이 존재한다는 사실을 알리고 전체 데이터를 거부하는 방식으로 동작합니다. 사용자가 잘못된 종류의 JSON 파일을 선택하였거나, 파일을 편집하는 과정에서 데이터 형식이 훼손되었을 가능성이 있기 때문입니다. 별도의 검증 절차 없이 데이터를 덮어쓰면 기존에 보관하던 지도 데이터가 모두 손실될 위험이 있으며, 일부 데이터만 정상적으로 변경되면 사용자가 왜 일부 장소 정보가 사라졌는지 이해하기 어려울 것입니다. 사용자가 명시적으로 실행한 작업에 관하여는 성공 또는 실패 여부를 명확하게 알려주는 것이 바람직합니다. 잘못된 데이터는 적용하는 시점에 엄격하게 차단하는 기본 원칙은 19장에서도 동일하게 적용될 것입니다.
[45] 다음은 사이드바 영역에 내보내기 및 가져오기 버튼을 연결하는 부분에 관하여 설명하겠습니다(【104】).
[46] 내보내기 기능은 브라우저에서 제공하는 표준 파일 다운로드 방식을 사용하여 구현하였습니다. 【105】와 【106】는 문자열 데이터를 실제 파일처럼 다룰 수 있게 하여 주는 객체입니다. 장소 데이터를 JSON 문자열로 변환한 뒤 Blob 객체로 생성하고, 【107】를 통하여 해당 Blob 객체를 가리키는 임시 주소를 생성합니다. 그 후 화면에 보이지 않는 링크 요소 【108】에 【109】 속성을 사용하여 저장할 파일 이름을 지정하고, 자바스크립트에서 해당 링크를 클릭하는 방식으로 다운로드를 실행합니다. 사용자의 입장에서는 일반적인 파일 다운로드 과정과 동일하게 보일 것입니다. 마지막에 호출하는 【110】 함수는 더 이상 사용하지 않는 임시 주소를 해제하여 메모리 자원을 반환하는 역할을 수행합니다.
[47] 가져오기 기능은 내보내기 기능과 반대의 순서로 동작합니다. 파일 선택 대화상자는 유형이 【112】인 숨겨진 입력 요소를 통하여 엽니다. 해당 입력 요소를 화면에서 보이지 않도록 【113】로 숨겨 두고, 사용자가 「가져오기」 버튼을 클릭하면 대신 【114】를 호출하여 파일 선택 창을 엽니다. 사용자가 파일을 선택하면 【115】 이벤트가 발생하며, 【116】를 통하여 선택한 파일의 내용을 문자열 형식으로 읽어옵니다. 그 후 읽어온 문자열을 【117】에 전달하여 처리합니다. 이때 중요한 점은 이 호출 부분을 try-catch 구문으로 감싸 예외 상황에 대비하였다는 것입니다. 앞에서 설명한 바와 같이 【118】는 내용에 문제가 있는 파일을 전달받으면 【119】를 통하여 에러를 발생시키도록 설계하였습니다. 발생한 에러는 이곳의 catch 블록으로 전달되어 【120】 형태로 사용자에게 알려지게 됩니다. 즉 데이터의 유효성 검사는 store가 담당하고, 발생한 에러를 사용자에게 알리는 역할은 sidebar가 담당하는 구조입니다. 마지막 라인에 위치한 【121】는 파일 선택 입력 요소의 값을 초기화하는 역할을 수행하며, 이를 통하여 동일한 파일을 연달아 다시 선택하여도 【122】 이벤트가 정상적으로 발생하도록 설정합니다.
[48] 자바스크립트 코드가 【123】 식별자를 통하여 찾고 있는 버튼 요소가 실제로 HTML에 존재하는지도 확인하여 보시기 바랍니다. 해당 버튼 요소가 없으면 【124】 관련 오류가 발생하여 사이드바 초기화 코드 자체가 실행되지 않고 중단될 수 있습니다. 프롬프트의 요구사항에 따라 【125】의 사이드바 영역 맨 아래에 내보내기 및 가져오기 두 개의 버튼이 정상적으로 생성되었는지 반드시 확인하여 주시기 바랍니다.
[49] 【126】는 파일 선택 창에서 기본적으로 보여줄 파일 형식을 지정하는 속성으로, JSON 파일 형식을 우선적으로 보여주도록 설정하는 힌트 정보입니다. 【127】는 앞에서 설명한 【129】 파일 형식을 지정하는 속성입니다. 【128】에는 내보내는 파일의 종류와 형식에 관한 정보도 함께 포함되어 있습니다.
[50] 이제 실제로 백업 및 복원 기능을 직접 사용하여 보는 실습을 진행하여 보겠습니다. 장소를 삭제하는 기능은 19장에서 구현할 예정이므로, 이번 시간에는 삭제로 인한 데이터 손실 상황 대신 【130】를 통하여 데이터가 손실된 상황을 연습하여 보겠습니다.

[55] Q1. 만약 데이터를 저장하는 코드를 【133】 한 곳에 통합하여 작성하지 않고, 장소를 추가·수정·삭제하는 각 기능 【134】에 별도로 작성하였다면, 추후에 어떤 문제가 발생할 수 있을까요?
[56] 데이터 저장 방식을 변경할 때 각 위치의 코드를 모두 찾아 수정하여야 하며, 일부 위치를 빠뜨리면 데이터가 정상적으로 저장되지 않는 문제가 발생할 수 있습니다. 또한 중복된 코드로 인하여 유지보수가 어려워지고, 저장 로직에 변경 사항이 생길 때마다 여러 곳을 수정하여야 하므로 작업 시간이 증가하고 오류가 발생할 확률이 높아집니다.
[57] 만약 저장 로직의 내용이 변경될 경우 모든 중복된 코드를 동일하게 수정하여야 하며, 일부만 수정하고 나머지는 수정하지 않아 동작 방식이 불일치하는 문제가 발생하기 쉽습니다. 또한 기능 추가나 개선 시 중복된 코드 각각에 동일한 변경 작업을 반복하여야 하므로 작업 효율이 낮아집니다.
[58] Q2. 【135】 가져오기 기능은 데이터 검증에 실패한 경우 일부 데이터만 수용하는 대신 전체 데이터를 거부하는 이유는 무엇일까요? 일부만 수용하는 방식과 비교할 때 장점과 단점은 무엇일까요?
[59] 사용자가 명시적으로 데이터를 교체하도록 요청한 경우, 일부만 변경되면 사용자는 어떤 내용이 변경되었고 어떤 내용이 문제가 있는지 정확하게 알 수 없습니다. 따라서 전체 데이터를 거부하고 실패 사실을 명확하게 알려주어 사용자가 파일을 수정하거나 올바른 파일을 다시 선택할 수 있도록 하는 것이 원칙입니다. 장점은 데이터의 일관성이 유지되고 사용자가 상황을 정확하게 인지할 수 있다는 점이며, 단점은 사소한 오류 하나로 전체 데이터를 사용할 수 없게 될 수도 있다는 점입니다.
[60] 반대로 일부 데이터만 수용하는 경우 사용자가 예상하지 못한 상태로 데이터가 변경되어 혼란을 겪을 수 있으며, 문제가 있는 부분을 찾아 수정하기도 어려워집니다. 전체를 거부하는 방식은 데이터의 정확성과 예측 가능성을 보장하지만, 데이터의 일부만 문제가 있음에도 전체를 사용할 수 없게 되는 경우가 발생할 수 있다는 단점이 존재합니다.
