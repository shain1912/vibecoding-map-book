[1] 4장에서 Claude Code를 설치하고 첫 작업을 시켜 보았습니다. 조금 더 쓰다 보면 불편한 점이 하나 생길 겁니다.

[2] Claude Code에게 일을 시키면, 에이전트가 파일을 읽고 코드를 고치는 동안 우리는 기다려야 합니다. 1~2분짜리 작업이면 괜찮겠지만, 큰 작업은 5분에서 10분씩 걸리기도 합니다. 그동안은 다른 일에 손을 대기 어렵겠지요. 그리고 이런 상황도 생길 수 있습니다.

[3] 일을 나눠서 동시에 진행하면 이런 답답함을 어느 정도 덜 수 있습니다. 에이전트를 꼭 하나만 써야 하는 것은 아닙니다. 여러 에이전트에게 서로 다른 일을 맡기고 각각의 결과를 확인하면 되겠지요.

[4] Orca를 쓰면 이렇게 일할 수 있습니다.

[5] Orca는 여러 AI 코딩 에이전트를 작업 공간 단위로 나누어 동시에 실행하는 도구입니다. 화면 왼쪽에 작업 목록이 카드 형태로 늘어섭니다. 카드 하나를 클릭하면 그 작업 전용 터미널이 열립니다. 이 작업 단위를 워크트리라고 부릅니다. 터미널마다 Claude Code 같은 에이전트를 하나씩 띄워 두고, 카드를 옮겨 다니며 진행 상황을 확인하면 됩니다.

[6] 그림 6.1 — 에이전트 한 명 vs 여러 명 지휘

[7] 이 책의 모든 실습은 Claude Code 하나만 있어도 따라갈 수 있습니다. Orca는 저자가 실제로 쓰는 방식을 소개하려고 넣은 내용이니 설치하지 않아도 됩니다. 터미널 하나도 아직 익숙하지 않다면 이 장은 읽기만 하고 넘어가세요. 책을 끝낸 뒤에 다시 돌아와도 됩니다. 여러 작업을 동시에 돌리면 편하기는 하지만 꼭 그래야 하는 것은 아닙니다.

[8] 에이전트를 여러 개 실행하려면 먼저 풀어야 할 문제가 하나 있습니다. 같은 폴더를 여러 에이전트가 함께 고치면 충돌이 생길 수 있습니다.

[9] 같은 폴더에서 에이전트 두 개가 동시에 일한다고 해 봅시다. A가 【1】를 고치는 중인데 B도 【2】를 고칩니다. 두 수정이 뒤섞이면 파일이 망가집니다. 에이전트마다 폴더를 따로 주어야 합니다.

[10] 여기서 3장에서 설치한 git을 다시 씁니다. git의 워크트리(worktree) 기능을 쓰면 저장소 하나에서 브랜치마다 독립된 폴더를 하나씩 더 만들 수 있습니다.

[11] 3장에서 브랜치를 실험용 갈래라고 설명했습니다. 보통 【3】으로 브랜치를 바꾸면 같은 폴더의 내용물이 통째로 바뀝니다. 브랜치는 여러 개인데 폴더가 하나뿐이라서 그렇습니다. 워크트리를 쓰면 폴더를 하나 더 만듭니다. 【4】를 한 번 실행하면 같은 저장소를 공유하는 폴더가 하나 더 생깁니다. 그 폴더에는 브랜치가 따로 붙습니다.

[12] 폴더가 세 개이므로 에이전트 세 개가 서로 방해하지 않고 동시에 일할 수 있습니다. 각자 자기 폴더에서 파일을 고치고, 결과가 좋으면 git으로 합치고(merge), 그렇지 않으면 폴더째 지웁니다. 폴더를 통째로 복사하는 것과 달리 워크트리는 저장소의 커밋 기록을 공유합니다. 그래서 용량도 아끼고 나중에 합치는 일도 수월하게 할 수 있습니다.

[13] 그림 6.2 — 워크트리 개념도

[14] 3장에서 커밋을 남겨 두면 이전 시점으로 되돌릴 수 있다고 했습니다. 워크트리를 쓰면 되돌릴 일 자체가 줄어듭니다. 에이전트에게 큰 수정을 시킬 때는 워크트리에서 하게 합니다. 그러면 원본 폴더의 잘 돌아가는 코드는 처음부터 손댈 일이 없습니다. 결과가 좋지 않으면 워크트리만 지우면 됩니다.

[15] 워크트리 명령이 실제로 어떻게 생겼는지 살펴봅시다. 굳이 외워야 하는 것은 아닙니다. Orca가 대신 실행해 주고, 필요하면 에이전트에게 【5】라고 시켜도 됩니다.

[16] 이 한 줄을 실행하면 저장소 옆에 【6】 폴더가 생기고 거기에 【7】라는 새 브랜치가 연결됩니다. 【8】를 입력하면 지금 열려 있는 워크트리 목록이 나옵니다. 다 쓴 워크트리는 【9】 명령으로 정리합니다. 워크트리를 다루는 명령은 이 셋이면 충분할 겁니다.

[17] 다만 워크트리를 직접 관리하려면 명령어를 기억해야 하고, 폴더가 늘어날수록 어느 폴더가 어떤 작업이었는지 헷갈릴 수 있습니다. 이 일은 Orca가 대신합니다. 버튼 하나로 워크트리를 만들고, 작업마다 카드로 정리하고, 다 쓴 워크트리는 지워 줍니다.

[18] Orca는 윈도우에서 동작합니다. 설치 파일과 최신 설치 방법은 공식 사이트에서 확인하세요. 이런 도구는 업데이트가 잦아서 책에 적어 둔 버튼 이름이 몇 달 뒤에 달라질 수 있습니다.

[19] 설치 순서는 여느 윈도우 앱과 크게 다르지 않습니다.

[20] 세부 화면이 책과 조금 다를 수 있습니다. 이 장에서 중요한 것은 버튼의 위치가 아닙니다. 워크트리 카드로 작업을 나누고 카드마다 에이전트를 실행한다는 구조가 중요합니다. 이 구조는 버전이 바뀌어도 같습니다. 설치 화면이 낯설면 화면을 캡처해서 Claude Code에게 【10】라고 물어보아도 됩니다.

[21] 그림 6.3 — Orca 첫 실행 화면 (구성 예시)

[22] Orca를 쓰려면 2장의 Node.js, 3장의 git, 4장의 Claude Code를 먼저 설치해야 합니다. 특히 워크트리는 git 기능입니다. 열려는 폴더가 git 저장소가 아니면 워크트리를 만들 수는 없습니다. 지도 프로젝트는 8장에서 만듭니다. 지금은 연습용 폴더에서 【11】을 해 보거나 화면만 확인하고 넘어가도 좋습니다.

[23] Orca에서는 워크트리 카드 하나가 작업 하나입니다. 카드마다 터미널이 하나씩 붙습니다. 쓰는 순서를 살펴봅시다.

[24] 먼저 작업 카드를 만듭니다. 새 워크트리를 만들면 카드가 하나 생깁니다. 카드에는 【12】처럼 작업 이름을 붙입니다. 내부적으로는 git이 새 브랜치와 새 폴더를 만들지만, 화면에서는 카드 한 장만 늘어납니다. 이름은 나중에 봐도 무슨 작업이었는지 알아볼 수 있게 짓는 편이 낫습니다. 【13】이나 【14】라고 적어 두면 며칠만 지나도 내용을 떠올리기 어려울 수 있습니다. 【15】이나 【16】처럼 작업 내용이 드러나게 적으세요.

[25] 그다음 카드의 터미널에서 에이전트를 실행합니다. 카드를 열면 그 워크트리 폴더에서 동작하는 터미널이 나옵니다. 여기서 4장에서 배운 대로 입력합니다.

[26] 입력할 것은 이 한 줄뿐입니다. 4장에서 쓰던 Claude Code와 같은 프로그램이 실행됩니다. 이 카드 전용 폴더 안에서 동작한다는 점만 다릅니다. 에이전트가 어떤 파일을 고치든 이 워크트리 밖으로는 나가지 않습니다. Orca를 쓴다고 해서 새로 배울 명령이 생기는 것은 아닙니다. 권한 프롬프트를 읽고 허용하는 습관도, 작게 시키고 확인하는 습관도 4장에서 익힌 그대로 쓰면 됩니다.

[27] 이제 평소처럼 일을 시킵니다. 프롬프트는 4장에서 배운 맥락·목표·제약·출력을 그대로 쓰면 됩니다.

[28] 그림 6.4 — 워크트리 터미널에서 실행한 Claude Code (구성 예시)

[29] 카드의 터미널은 일반 터미널과 같으므로, Claude Code 대신 다른 CLI 에이전트를 실행해도 됩니다. 4장 끝에서 소개한 codex 같은 무료 대안도 쓸 수 있습니다. 어떤 카드에는 Claude Code를, 어떤 카드에는 codex를 띄우는 식입니다. 저자는 한 에이전트가 만든 코드를 다른 회사의 에이전트에게 검토시킬 때 이 방법을 씁니다. 같은 모델끼리는 비슷한 실수를 나란히 놓치기 쉽지만, 다른 회사의 모델은 그 부분을 짚어 주는 경우가 많기 때문입니다.

[30] 이제 카드를 여러 장 만들어 봅시다.

[31] 예를 들어 지도 앱을 만들다가 이런 상황이 되었다고 합시다. 할 일이 셋인데 서로 건드리는 파일이 다릅니다.

[32] 카드 세 장을 만들고, 각 터미널에서 에이전트를 실행하고, 각각 프롬프트를 입력합니다. 그러면 세 작업이 동시에 진행됩니다. 우리는 카드를 오가며 진행 상황을 확인하고, 에이전트가 묻는 것(권한 허용, 선택지 결정)에 답하면 됩니다. 무엇보다 기다리는 시간을 크게 줄일 수 있습니다. A가 작업하는 동안 B를 확인하고, B가 작업하는 동안 C에게 다음 일을 시킬 수 있습니다.

[33] 어떤 일을 동시에 진행해도 되는지 판단하는 기준은 하나입니다. 한 작업의 결과가 다른 작업에 필요한지 보면 됩니다. 검색 기능과 사이드바 디자인은 서로의 결과가 필요 없으므로 동시에 진행해도 됩니다. 반면 【17】와 【18】는 앞의 결과 위에 뒤의 작업이 쌓이므로 순서대로 시켜야 합니다. 서로 독립적인 일은 동시에, 앞의 결과가 필요한 일은 차례대로 진행합니다.

[34] 작업이 끝난 카드는 두 가지 중 하나로 처리합니다. 결과가 좋으면 그 워크트리의 브랜치를 main으로 합칩니다(merge). git이 처리하는 작업이므로 에이전트에게 【19】라고 시켜도 됩니다. 결과가 좋지 않으면 카드를 지웁니다. 워크트리를 지워도 원본 폴더는 그대로입니다.

[35] 그림 6.5 — 카드 세 장이 동시에 굴러가는 모습 (구성 예시)

[36] 같은 파일을 고치는 작업 두 개를 동시에 진행하면 안 됩니다. 폴더가 따로 있으니 작업 중에는 문제가 없습니다. 그러나 나중에 두 브랜치를 합칠 때 같은 파일의 같은 부분이 다르게 고쳐져 있으면, git이 어느 쪽을 반영할지 묻습니다. 이런 상황을 충돌(conflict)이라고 합니다. 해결하지 못할 문제는 아닙니다. 다만 처음 겪으면 손을 대기가 쉽지 않을 겁니다. 동시에 진행할 작업은 서로 다른 파일을 건드리는 것으로 고르세요. 그리고 에이전트를 여러 개 실행하면 4장에서 이야기한 요금제 한도도 그만큼 빨리 줄어듭니다.

[37] 저자가 이 책과 예제 앱을 만들 때 실제로 쓰는 구성을 소개합니다.

[38] 예를 하나 들면 이렇습니다. 카드 1에서는 Claude Code가 지도 앱의 새 기능을 만듭니다. 카드 2에서는 다른 에이전트가 전날 쓴 원고의 오탈자와 어색한 문장을 검토합니다. 카드 3에는 바꿔 볼 만한 수정을 시켜 둡니다. 카드 1 → 2 → 3 순서로 돌아보며 질문에 답하고, 끝난 작업을 합칩니다. 세 카드 모두 마음에 들지 않는 결과를 내서 전부 지운 날도 있습니다. 그래도 워크트리에서 작업했으므로 원본 코드에는 아무 영향이 없었습니다.

[39] 필요한 것은 순서입니다. 시키고, 다른 카드를 확인하고, 결과를 검토하고, 합칩니다. 이 순서에 익숙해지면 혼자서도 여러 작업을 동시에 진행할 수 있습니다. 코드를 직접 쓰는 대신 무엇을 시킬지 정하고 결과를 판단하는 일에 시간을 씁니다.

[40] 그림 6.6 — 저자의 작업 화면 배치도

[41] 이 구성을 꼭 따라야 하는 것은 아닙니다. 다음 장부터 나오는 실습은 모두 터미널 하나와 Claude Code 하나로 진행할 수 있게 써 두었습니다. 다만 책 후반부에서 기다리는 시간이 길게 느껴지면, 그때 이 장으로 돌아와 카드를 두 장으로 늘려 봐도 좋습니다.
